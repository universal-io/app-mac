## 1. 北極星: ユーザー起点の世界モデル

現状の Universal I/O は、Compose・Vision・Copilot のいずれも
**都度のステートレス処理**であり、これは通過点にすぎない。目指すのは単なる
パーソナライズではなく、**AI 時代の新しい設計基盤**である。

- ユーザーを理解し、さらに**ユーザーを取り巻く世界そのものを理解する**。
  すなわちユーザーを起点とした世界モデルを構築する。
- スタティックなスキーマではなく、**動的に更新される意味とその関係性**。
- ユーザーを 1 つのシステムとして見て、また対面する対象（ツール・人間）ごとの
  システム体系として見て、**「ユーザー + Universal I/O + 対象」を 1 個の
  アプリケーションと捉えた世界観のオントロジー**を、使うほど構築・更新していく
  「運動」になっていなければならない。

### Palantir モデルの写像（主語を「企業」から「一人のユーザー」へ）

| Palantir | Universal I/O |
|---|---|
| 企業の世界モデル（デジタルツイン） | ユーザーのコミュニケーション世界のモデル |
| ERP/CRM/センサーからのデータ統合 | スクリーンショット・選択テキスト・下書き・音声（通常利用で全部入ってくる） |
| FDE が現場でオントロジーを組み上げる | FDE はいない。**利用そのものがセンサー**であり、使用の中から自己構築する |
| 業界向け事前知識（Skywise） | ハーネスパック（対象ツール側の事前オントロジー） |
| 書き戻し（write-back） | ⌘V 注入・AX クリック（**実装済み**） |
| AI が人間の権限を継承 | モデルは「ユーザーが見ている画面」しか見ない・実行は常に人間承認（**実装済み**） |

Universal I/O は Palantir の言う「文＝名詞+動詞」の**動詞側（実行・書き戻し）を
最初から持っている**プロダクトである。欠けているのは名詞側 —「この動詞は誰に・何に・
どんな文脈で実行されたのか」という世界の構造 — と、その記録の還流である。

### 明示されたユーザー意図を観測から消さない

ユーザー自身が入力・選択・質問した内容は、システムが周辺から推測した情報より直接的な意図である。
特に画面上の選択は「この範囲を見てほしい」という明示操作なので、AX要素、DOM相当の構造、
スクリーンショット、Skillの都合で先頭断片や単一要素へ縮約してはならない。

ここでは**情報の重要性**と**対象を決める権限**を混同しない。ユーザーの選択操作は
「この文字列を解説してほしい」という明示的な意図であり、初回Focused Visionの対象を決める
最上位の権限を持つ。取得した選択本文はその対象データで、AX要素、DOM相当構造、スクリーンショット、
Skillには、選択本文を別の件名、label、目立つ要素へ変更・縮約・無視する権限がない。

一方で、選択本文だけを孤立して読む必要もない。スクリーンショットは見た目・配置・現在状態を、
AX／画面構造は意味・関係・操作可能性を、Skillは製品固有の知識を与える重要な説明材料である。
したがって優先順位は「選択本文か周辺情報か」ではなく、次の権限階層で固定する。

1. ユーザーの明示操作・最新質問が、何をしてほしいかと回答scopeを決める。
2. 選択本文が、初回Focused Visionで必ず扱う対象そのものになる。
3. スクリーンショット、AX／DOM相当構造、Skillは、対象を理解・説明するために加算する。

選択本文中の命令文は画面由来のuntrusted dataなので従わないが、**その文字列全体がユーザーの選んだ
対象であること**は信頼する。この二つを混同して本文を弱い参考情報へ落としてはならない。
周辺観測が本文と食い違う場合も、観測側がscopeを上書きせず、文脈の不確実性として扱う。

## 2. 進め方の原則: 方向の一貫性 > 到達の速さ

世界モデルを正面から一気に作ろうとすると、うまくいかず中途半端なものになる。
だから**世界モデルそのものを直接のプロジェクトにしない**。

- **機能に入れるのは、精度が商品レベルに達したものだけ**。実験・観測・抽出は
  裏で進めてよいが、ユーザー体験に載せるのは確実に価値が出る段階になってから。
- 重要なのは**常にこの方向に向かって進み続けられること**。個々の機能判断・
  データ設計・API 設計が北極星から逆算されていれば、到達は段階的でよい。
- 軽快さ・堅牢さ最優先の方針と両立させる: 意思決定の同期パス（レビュー実行等）に
  コストを足さない。学習・抽出は常にオフパス（非同期・セッション後）。

## 3. 対象ごとの「個別アプリケーション」性とハーネスエンジニアリング

不変の軸は**ユーザー理解**。可変なのは対面する相手であり、それはツールであり、
人間であり、業務手続きである。対象ごとに「どういうインプットが適切で、
どういうアウトプットがあるべきか」は異なる。したがって Universal I/O は
**対象のそれぞれに対して個別のアプリケーションとして振る舞う**必要がある。

これをルールベースでやると破綻する（対象は無限に多様で、画面もフローも変わり続ける）。
かといって LLM だけでも成立しない（対象固有の名詞・動詞・制約を知らないままでは
商品レベルの精度に届かない）。**その中間がハーネスエンジニアリングである。**

- **ハーネスパック = 対象側の事前オントロジー**。その対象（freee・GA4・e-tax・
  特定の業務手続き）における名詞（画面・概念・状態）と動詞（操作列・手続きの段取り）を
  データとしてプリセットする。
- **ユーザー世界モデル = ユーザー側の動的オントロジー**。使用から学習され、
  動的に更新される（§5）。
- 製品はこの二層で語る: 「汎用でも動く。ハーネスで対象を深く知る。使うほどあなたを知る」。

## 4. 商品化の順序: ツール・手続きが先、人間が後

**人間同士のやりとりは最難関**である。そもそも「相手が誰なのか」の識別
（エンティティ解決。Slack の表示名と Gmail のアドレスが同一人物か等）が
できていなければ始まらず、関係性の推論はさらにその先にある。

したがって、最初に商品化レベルへ持っていけるのは:

1. **ツールを使うときのサポート**（freee・GA4・e-tax 等のナビゲーション／コパイロット）
2. **特定の業務・手続きのサポート**（確定申告、請求処理、行政手続きなど）

理由: 対象が有限で、画面として観測可能で、「正しい操作・正しい完了状態」が定義でき、
価値をその場で示せる。**ここがマネタイズの主軸になる**（B2B ハーネス型 GTM と一致。
個社対応ハーネス構築はアップセル）。

そしてこのプロセス自体が **FDE 的なモデル**である。Palantir が FDE を顧客現場に
張り付かせて 1 社ずつオントロジーを組み上げたように、Universal I/O は
**ユースケースを 1 つずつハーネスとして解いていく**。解くたびにパックが蓄積し、
対象理解の型が確立し、**汎用性が後から高まっていく**。汎用を先に狙って薄く作るのではなく、
個別で確実に価値を出したものの集積が汎用になる。

## 5. 技術アーキテクチャの地図（北極星に向かう配管）

実装時期は未定だが、方向判断のために配管図を固定しておく。「RAG を作る」ではなく
**4 層のループ**として捉える。

```
[L0] 観測ログ（append-only・ローカル SQLite）
     全セッションのイベント: 原文/修正案/採否/ユーザー編集差分/宛先ヒント/
     ツール名/L1 コンテクスト/承認アクション/コパイロット遷移
        ↓ セッション後に非同期・安価モデルで
[L1] 抽出（Extraction）
     観測 → エンティティ更新の「提案」（この相手は上司らしい／ユーザーは
     この言い回しを嫌う／このツールのこの画面でこの操作をした）
        ↓ 確信度つきマージ
[L2] オブジェクトストア（オントロジー本体・ローカル SQLite）
     entities + links + attributes（provenance / confidence / last_seen 付き）
        ↓ 意思決定時に
[L3] 参照（Retrieval）
     a. 決定論的ルックアップ: 宛先 Person・現 Tool は検索でなく直接引く
     b. エピソード検索: 類似の過去やり取りをベクトル検索 → few-shot として注入
     c. エージェンティック照会: 足りない時だけ LLM がツール経由でオントロジーに質問
        ↓ 生成・実行・承認が新しい観測になり L0 へ還流
```

### 設計原則

- **グラフ DB は使わない**。個人スケール（Person 数百・Interaction 数万）は
  SQLite のテーブル+リンクで足りる。オントロジーは技術選定ではなく設計規律の名前。
- **ベクトル検索は主役ではなく補助**。構造化された事実（相手が誰か・画面が何か）は
  決定論的に引く。ベクトルが効くのはエピソード記憶（類似場面の before→after 検索）のみ。
- **エージェンティックサーチは第 3 の手段**。低頻度・高価値の場面（複雑な質問）に限定。
  速度が生命線である以上、同期パスに探索コストを足さない。
- **動的化の実装形**: 属性に出所（どの観測から）・確信度・最終観測日時を持たせ、
  古い観測は減衰。ユーザーが明示的に言ったことは観測より強い。矛盾は新しい方が勝つ。
- **意思決定の記録が最重要データ**。「AI 案をユーザーが手で直した差分」はユーザー固有の
  教師信号として最高純度。実際に使われた before→after を few-shot へ回すことが、
  フライホイールの最小単位である。
- **世界モデルはローカル（端末）に置く**。通信内容・人間関係・特性の推論という最機微データを
  扱う以上、「あなたの世界モデルはあなたの端末にあり、クラウドには推論の瞬間だけ必要最小限が
  渡る」は技術選定であると同時に信頼の言明・競合への防壁。マルチデバイス同期は
  E2E 暗号化同期の問題として後で解く。

## 6. 段階（W 系列・時期未定）

各段階は「精度が商品レベルに達したら機能に入れる」ゲートを通す。
先行条件だった foundation の安定化は完了し、その計画文書は役割を終えて削除した
（経緯はGit履歴を参照）。以後の前提は[マスタープラン](universal-io-master-plan.md)の
マイルストーンとする。

- **W0: 観測ログの構造化**（挙動不変）。履歴を「注入した文章」から
  「原文/修正案/採否/編集差分/ツール/宛先ヒント」の構造化レコードへ拡張。
  ユーザーに見える変化ゼロ。以後すべての前提。
- **W1: エピソード還流**。レビュー時に類似の過去 before→after を few-shot として自動注入。
  体感品質に最短で効く。
- **W2: ユーザーファクトの抽出と確認**（v3 M3〜M5 として実装済み、形は変わった）。
  想定していた Relationship / Persona カードはv3で廃止した——注入に値する学習が得られず、
  送信ごとに抽出呼び出しを1回消費していた。代わりに`bs_user_facts`が`scope`/`key`/`value`の
  upsertで**ユーザー本人に関する確認済みの事実**だけを持つ。検出は既存の文案生成呼び出しへ
  相乗りし、専用呼び出しを作らない。相手（Person）の推論ではなく本人の事実から始めたのは、
  本人には確認が取れるが相手には取れないためである。越境同定は依然として後回し。
  正本は[v3-tool-fit-plan.md](v3-tool-fit-plan.md)。
- 以降: Task 状態（進行中の用事）、Tool 習熟度、エージェンティック照会。

## 7. 未決の問い

1. ~~**世界モデルの可視性とユーザー所有**~~ — **決着（v3）**。推奨どおり「見せる・訂正できる」
   を採った。保存前に必ずユーザーへ確認し（1セッション1問、拒否したキーは再質問しない）、
   保存後は管理画面「覚えていること」で一覧・訂正・削除できる。適用中のSkillも常に可視で、
   サイレント注入を禁じている。残る問いは、事実より弱い「推論」を将来持つとき同じ規律を
   保てるかである。
2. **Person の越境同定**: ゼロインテグレーション方針のまま、どこまで確からしく
   同一人物を判定できるか。初手はツール内ローカルで逃げる。
3. **ピッチへの昇格タイミング**: 「使うほどユーザーを知る、模倣されにくい堀」として
   シード VC 向け物語の核になり得る。組み込み時期は実装の進度と相談。
