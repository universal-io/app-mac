# 速さ（R13）

最終更新: 2026-08-06 ／ ステータス: L1・L2実機確認済み、L3〜L5計測・改善中

進捗と受け入れ条件の正本は[マスタープラン R13](universal-io-master-plan.md)、
本書は原因分析・目標構造・マイルストーンの正本とする。

R11が「無音で止まらない」、R12が「動いているのに内容が正しくない」を扱うのに対し、
本プロジェクトは**正しいが遅い**を扱う。

## 0. なぜ

このアプリはホットキーで呼ばれる。呼ばれた時点でユーザーは助けを求めており、
待たされるほど「自分でやった方が早い」に近づく。**すぐパネルが出て、すぐ解説が始まること**が
機能そのものと同じ重さを持つ。

速くする手は3種あり、順序が違うと無駄になる。

1. 無駄を削る（本当に払っている費用を減らす）
2. 順序を変える（払う費用は同じでも、待っている間に読めるものを出す）
3. モデルを選ぶ（同じ仕事をより速い一次モデルで行う）

3は最後である。R12 §1-eの判断をそのまま引き継ぐ：**入力が壊れた状態でモデルを比べても、
モデルの差ではなく入力の壊れ方を測ることになる。**

## 1. 実測

### 1-a. 区間ごとの計り方が揃っていなかった

R11までに入っていた計測は、AX走査・identity解決・Gateway往復を**それぞれ独立のストップ
ウォッチ**で測っていた。これらは設計上**並行**して走る（撮影とAX読みは同時）ため、足し算に
意味がない。さらにユーザーが体感する2つの区間、

- ジェスチャからパネルが出るまで
- Gatewayが返ってから画面に出るまで

はどちらも計測されていなかった。「Visionが遅い」という報告に、記録から答えられなかった。

`SummonClock`を導入し、**ユーザーが求めた瞬間**という単一起点を全記録へ通した。起点は
初回ターンがダブルタップ、質問ターンがEnter、Copilotステップがクリックである。カメラボタン
経由の範囲選択は人間がドラッグしている時間なので、アプリが仕事を引き取る時点へ起点を置き直す。

現在の記録（`Diagnostics`、release buildでも残る／管理画面「設定 › 動作記録」）:

| event | 内容 |
|---|---|
| `coordinator.panelShown` | ジェスチャからパネル表示まで |
| `coordinator.axFocusResolved` | 撮影とAX snapshotの完了 |
| `vision.axCollected` | AX走査のpass数、経過、候補数、`gained`、打ち切り理由 |
| `vision.request` | リクエスト発射まで（`sinceAsk`）と、その内訳 |
| `vision.firstContent` | **最初に読めるものが出た瞬間**と、その経路（`stream` / `result`）。時間だけを扱う |
| `vision.image` | Gatewayへ送った画像の幅・高さ・KB |
| `vision.serverTiming` | サーバー内訳（body／auth／quota／provider／total）。差が回線 |
| `vision.preflight` | Supabase preflightの内訳（verifyJWT／tenantEntitlement／plan／count） |
| `vision.result` | 回答のmode、ハイライトの結末（`none` / `resolved` / `unresolvable`）、候補数 |
| `vision.turn` | ターン完了 |
| `copilot.capture` / `copilot.request` / `copilot.turn` | Copilotステップの同じ梯子 |

### 1-b. Copilotの進捗ターンは本番ビルドで1行も記録されていなかった

R12 §1-kで実測したとおり、`copilot`経路の撮影とAX走査は`#if DEBUG`のNSLogだけだった。
数字が1セッション分しか無いのはこれが理由で、そのセッションもDebugビルドだった。
`copilot.capture` / `copilot.request` / `copilot.turn`を追加し、本番でも見えるようにした。

`copilot.capture`は**撮影の試行回数**を含む。`StableScreenCaptureService`は最大8回撮り、
各回のあいだに350msの待機を挟む。しきい値`0.05`を超える変化が見つからない画面では
**構造上8回全部を使い切る**ので、R12 §1-aのログにある約5秒はここである。

### 1-c. AX走査の2パス目は無条件に走る

`stillGrowing`は1パス目で`previousVisited = 0`と比較するため、ノードが1つでもあれば必ず真になる。
web areaが無い場合は`coldWebContent`が真になる。**どちらの分岐でも2パス目が走る。**
R12 §1-kの実測は11回中11回とも2パス目が走り、11回とも結果が1パス目と完全に同一だった。
コストは583〜754ms（500msの待機＋走査）。

**ただし直していない。** 標本は1台・1セッション・すべて温まったツリーで、この待機の目的は
cold Chromiumのweb areaが現れるのを待つことである。方針を変えるには実使用の数字が要る。
`vision.axCollected`の`gained`（1パス目以降に増えた候補数）がその判断材料になる。

### 1-d. 「ストリーミング」は配管だけで、逐次ではなかった

reviewのSSE封筒はGatewayからmacOSクライアントまで通っていた。しかし
**どのプロバイダ呼び出しも`stream: true`を送っていなかった。** `runReviewStream`は
`runReview`の完了を待ってから全文を1つの`delta`として送る。したがってreviewの体感遅延は
非ストリーミングと同じである（api-contract.mdに明記した）。

Visionにはそもそも封筒すら無く、モデルがJSONで答えるため**閉じ括弧まで1文字も出せない**。
必要な一文が先に完成していても、生成の全部が待ち時間だった。

### 1-e. プロバイダのストリーミング契約（実測、2026-08-05）

`gpt-5.6-luna`のResponses APIへ`stream: true`と現行と同一の`strict: true` json_schemaで
リクエストし、イベントを数えた（リポジトリ外の短命probe、§5）。

```text
HTTP 200  content-type=text/event-stream
 183  response.output_text.delta      ← delta フィールドは string
   1  response.output_text.done
   1  response.completed              ← response に status / output / usage
   1  response.created / in_progress / content_part.added / added / done
accumulated deltas == completed の output text : true
strict json_schema の結果として parse できる    : true
```

**実装が置いた仮定はすべて成立した。** 増分の連結は最終テキストと一致するので、
`response.completed`をそのまま既存の非ストリーミングと同じ検証経路へ渡せる。

### 1-f. 待ち時間の大半は生成ではなく最初のトークンまでである

同じprobeで画像サイズを変えて測った。

| 画像 | input_tokens | 最初のdelta | message完成 | 完了 |
|---|---|---|---|---|
| 2560×1600（現行＝Retina実寸） | **4,927** | 5,057ms | 5,760ms | 5,992ms |
| 1280×800（論理解像度相当） | **1,327** | 1,901ms | — | 2,955ms |
| 33KBのアイコン（参考） | 203 | 2,284ms | 2,578ms | 3,290ms |

**絶対値は本番の値ではない。** このprobeは手元の回線から641KBのPNG（base64で855KB）を
アップロードしており、Vercelのデータセンターからの送信ではない。R12が記録した実測
「実画面サイズで一次985ms」とは条件が違うので、絶対値を比較してはならない。

**回線に依存しない数字はトークン数である。** 2560×1600で4,927トークン、1280×800で1,327
トークン。**線形寸法が2倍になると画像トークンは約3.7倍になる。**
アプリが送っているのはRetinaの実ピクセルなので、論理解像度で足りるなら prefill の計算量は
4分の1近くになる。

一方、ストリーミングが取り戻せるのは**生成の尾**だけである。上の表では約0.9〜1.0秒
（message完成から完了まで、および最初のdeltaから完了まで）。

### 1-g. ハイライトが出ないという報告と、その切り分け（2026-08-05）

L2投入後の実機で「Vision・Copilotともに該当箇所のハイライトが出なくなった」という報告を受けた。

**ストリーミングは原因ではない。** 本番の`runVision`と`runVisionStream`へ同一の画像・質問・
候補6件を与えて交互に3回ずつ実行した結果、**両方とも3/3で同じ候補（`c2`＝「レポート」）を選び、
mode=guideも一致した**（リポジトリ外probe、§5）。差分もハイライト解決部
（`VisionSession.apply`の`targetCandidateID`分岐、`showLiveHighlight`、
`VisionSessionView.previewHighlight`）を1行も変更していない。

**しかし当時の記録では、この問いに答えられなかった。** ハイライトが出ない理由は3つあり
（モデルが対象を選ばなかった／選んだが画面に置けなかった／描いたが見えない）、
どれであるかを示す記録が無かった。さらに`vision.firstContent`へ載せていた`mode`は、
ストリーミングが先に発火すると失われる作りだった。**計測が先に必要だという本プロジェクトの前提を、
自分の計測で破っていた。** `vision.result`（mode／highlight／candidates）を追加し、
`vision.firstContent`は時間だけを扱うようにした。

**同じログに、以前から測られていた別の容疑者がある。**

```text
vision.axCollected passes=2 elapsed=2503ms candidates=137 gained=0 webArea=true truncated=deadline
vision.axCollected passes=3 elapsed=4317ms candidates=280 gained=76 webArea=true truncated=deadline
```

**この画面ではAX走査が毎回1秒の期限に当たって打ち切られている**（`Budget.deadline = 1.0`）。
R12 §1-hの実測では、打ち切りで落ちるのは**まさに案内したいボタン**（ダウンロード系3つ、
タブバー、入力欄など）だった。候補137件が返っていても対象が入っていない状態はあり得る。
これはR12 E4／本書L4の領域で、L2とは無関係な既存の欠陥である。

**確定した（guidance-accuracy-plan.md 1-o）。** 実機で質問ターンは`highlight=resolved`で
リングが出ており、Vision側は動いている。Copilotで消えるのは**進捗ターンがハイライト対象を
選ばない**ためで、`apply`が`hide()`を呼ぶ。原因は候補集合ではなく、進捗ターンが前の画面も
会話履歴も持たないこと（R12 1-b／E3）。ストリーミングとは無関係である。

### 1-h. AX走査の費用は待ち時間ではなく1ノードあたりの往復回数だった（実測、2026-08-05）

「AXをどこまで取るか、どこから諦めるか」を決める前に、**1秒が何に使われているか**を測った。
実機5アプリ、同じツリーに対して1つずつ条件を変えた走査（リポジトリ外probe、§5）。

**本番は1ノードごとに7回の個別`AXUIElementCopyAttributeValue`を呼んでいた**
（role、subrole、label候補4つ、children）。`AXUIElementCopyMultipleAttributeValues`で
**1往復にまとめると、候補は1件も変わらないまま2.3〜5.7倍速くなる。**

| アプリ | ツリー全体 | 個別読み | まとめ読み | 倍率 | 候補の同一性 |
|---|---|---|---|---|---|
| VS Code | 3,443ノード / 264候補 | 3,259ms | 376ms | 8.7x | 一致 |
| VS Code（再測2回） | 3,426 / 262 | 1,144 / 1,218ms | 249 / 295ms | 4.1〜4.6x | 一致 |
| Google Chrome | 1,688 / 82 | 540ms | 177ms | 3.1x | 一致 |
| Xcode | 812 / 0 | 549ms | 97ms | 5.7x | 一致 |
| Slack | 448 / 67 | 112ms | 39ms | 2.9x | 一致 |
| Finder | 269 / 13 | 1,103ms | 474ms | 2.3x | 一致 |

候補は件数だけでなく**role・label・矩形のフィンガープリント列で突き合わせた**（件数の一致は
結果の一致ではない）。VS Codeの初回だけ不一致が出たが、差分は開いていたモデル選択メニューの
項目8件で、2回の走査の間にUIが変わったものだった。静止状態での再測3回はすべて一致した。
これはR12 §1-iのツリー不安定性が、矩形だけでなくlabelとメニューの存在にも及ぶという追加証拠である。

**まとめ読みはばらつきも小さい。** 個別読みのVS Codeは3,259ms→1,144msと3倍ぶれたが、
まとめ読みは376→249msに収まる。期限で打ち切る設計では、平均だけでなくばらつきが効く。

#### 2,000ノード上限は、まとめ読みによって「保護」から「欠落の原因」へ変わった

`maxNodes = 2_000`は1ノード7往復の時代に決めた値である。まとめ読み後は2,000ノードが
約180msで終わるため、上限が先に当たって残りの800msを使わずに打ち切る。実測ではVS Codeの
3,300ノードのツリーが**61%**、以前の6,885ノードのツリーが**29%**で切られていた。

そこで**期限（1.0秒）は動かさず、ノード上限だけを8,000へ上げた。** 測ったツリーはすべて
8,000に収まり、まとめ読みのブラウザ換算で8,000ノードは約800ms。**ユーザーの待ち時間の上限は
今日と同一のまま、同じ1秒でツリーの数倍を見る。** 遅くなる経路は原理的に無い。

#### 却下: 撮影範囲外のサブツリーを刈る

「上から順に取得すると取得しきれないなら重要なものだけ」への最初の案として、
frameが撮影範囲と交差しないノードの子孫を辿らない方式を測った。**危険なので採らない。**

- 効果が無い: 撮影範囲外と**証明できた**ノードはChrome 0件／Slack 0件／VS Code 0件。
  frameを持たないノードが Chrome 1,162/1,688、Xcode 798/812 もあり、
  「不明」は「不在」ではないので辿らざるを得ない（R10.5と同じ規則）。
- **Xcodeで壊滅した**: 812ノードのツリーが**2ノード**になった（reach 0%）。frameが撮影範囲外と
  報告された最上位コンテナ1つを刈った結果、その内側の810ノードすべてを失った。
  コンテナのframeは子孫の位置を代表しない。
- Finderだけは効いた（474ms→169ms、offCapture 35/269、候補は13/13維持）。しかし
  1アプリの利得と1アプリの全損は釣り合わない。

**測ってから実装したので、実装していない。** これは推測で入れていたら実機で初めて分かる欠陥だった。

### 1-i. 実機での確認と、画像を論理解像度へ落とす判断（2026-08-05）

L1・L2・AXまとめ読みを入れたビルドで、Kinstaのサイト情報画面（Chrome、プルダウンを開いた状態）を
実機で通した記録。

```text
coordinator.panelShown  sinceSummon=568ms
vision.axCollected      passes=2 elapsed=791ms  candidates=129 gained=0 truncated=complete
vision.firstContent     turn=first    sinceAsk=8077ms via=stream
vision.turn             turn=first    sinceAsk=8692ms gatewayRoundTrip=7733ms
vision.result           mode=observation highlight=none     candidates=0
vision.firstContent     turn=question sinceAsk=3030ms via=stream
vision.turn             turn=question sinceAsk=4031ms gatewayRoundTrip=4015ms
vision.result           mode=guide       highlight=resolved candidates=129
copilot.capture         attempts=2 -> copilot.request ax=804ms -> copilot.turn gatewayRoundTrip=4808ms
vision.result           mode=guide       highlight=none     candidates=131
```

**AXまとめ読みは実機で効いた。** 同じKinsta画面が以前は`elapsed=2503ms candidates=137
truncated=deadline`、今回は`elapsed=791ms candidates=129 truncated=complete`である。
3.2倍速くなり、打ち切りが消えた。**期限は1.0秒のまま**なので、速くなった分がそのまま
取得範囲に変わっている。

`gained`はこれで7標本のうち6つが0、1つが76になった。まとめ読み後の1パスは約150msなので、
791msの大半は**2パス目の前に置かれた500msの待機**である。L4の残りはここに絞られた。

**待ち時間の主因はGateway往復（7,733 / 4,015 / 4,808ms）で、その中身は画像である。**
この画面のスクリーンショットは3380x1892で、画像トークンは**7,756**だった。

#### 論理解像度で足りるか（R12 E6の合格条件を直接測った）

同じ実画面を縮小し、**開いたメニューの全行を書き起こさせて**正解11文字列との一致を数えた。
案内ではなく転写を課題にしたのは、モデルはメニューを読み違えたままもっともらしい案内を
出せるので、案内では失敗が隠れるからである。

| 画像 | 倍率 | input_tokens | メニュー | 小さい文字（SFTPホスト/ポート/ユーザー名/IP/環境名/PHP） |
|---|---|---|---|---|
| 3380x1892 | 1/1（現行） | **7,756** | 11/11 | 5/6 |
| 1690x946 | **1/2（論理解像度）** | **2,032** | **11/11**（3回とも） | **5/6（1/1と完全同一）** |
| 1127x631 | 1/3 | 988 | 11/11 | 4/6（PHP版の書式差） |
| 845x473 | 1/4 | 610 | 11/11 | 4/6 — **ポート41411を4141と誤読** |
| 675x378 | 1/4.5 | 440 | **9/11** | — |
| 563x315 | 1/6 | 340 | **7/11** | — |

**1/2は1/1と区別できない。** 唯一の誤り（`wealthparkincltd`に空白が入る）は**1/1でも同じように
起きる**ので、解像度の問題ではない。トークンは7,756→2,032で**3.8分の1**になる。

**壊れ方は「読めない」ではなく「幻覚」である。** 1/4.5では「次に適用する」が「次に進む」、
「他のサイトに反映」が「他のサイトに戻る」になった。1/6では「本番環境」「ステージング環境」と
完全な作り話になった。読めないと言わずに自信を持って間違えるので、**限界の手前で止まる必要がある。**
1/2は限界（1/4と1/4.5の間）まで2段の余裕がある。

検証は`sips`ではなく**本番と同じ`NSBitmapImageRep`＋`imageInterpolation = .high`**で縮小した
画像に対して行った（リサンプラーが違えば結果が違うため）。3回とも11/11、小さい文字も1/1と同一。

そこで**Gatewayへ送る画像だけを論理解像度（1ピクセル=1ポイント）へ落とす。** 倍率は
`pixelWidth / captureRect.width`から求めるので、特定のMacを仮定しない。ディスク上の画像と
`captureRect`は変えないので、候補矩形は撮影範囲に対する比率であり**ハイライトの座標計算は無影響**である。

**標本は1画面である。** 2つの異なる課題（メニュー転写・小さい値の転写）と3回の反復で確かめ、
限界点も特定したが、他の画面では未確認である。**案内の正確さが落ちたら最初に戻すのはここ。**
送信サイズは`vision.image`（width／height／kb）に記録してあるので、後から突き合わせられる。

### 1-k. モデル時間は安定していて、ばらつきは全部その外にあった（実測、2026-08-05）

画像を論理解像度へ落としたビルドの実機記録と、Supabase `bs_usage_events` に残ったサーバー側の
実測を突き合わせた。**クライアントが待っている時間の1〜4.3秒は、モデル呼び出しではない。**

| | クライアント `gatewayRoundTrip` | サーバー `latency_ms`（モデル呼び出し） | 差 |
|---|---|---|---|
| 15:19 初回 | 7,733ms | 3,523ms | **4,210ms** |
| 15:19 質問 | 4,015ms | 2,843ms | 1,172ms |
| 15:19 Copilot | 4,808ms | 2,772ms | 2,036ms |
| 15:42 質問 | 7,111ms | 2,815ms | **4,296ms** |
| 15:42 Copilot | 3,438ms | 2,447ms | 991ms |

**モデル時間は2,447〜3,523msに収まっているのに、クライアントの待ちは3.4〜7.7秒でばらつく。**
体感のばらつきは、これまで1つも計測していなかった区間にある。候補はJSON本体の読み取り
（画像がbase64で約750KB）、`authenticate`、`enforceQuota`、アップロード、TLS、応答転送である。

transcribeは以前から`meta.timing_ms`で`auth` / `quota` / `provider` / `usage` / `total`を返して
いた。**Visionは返していなかったので、同じ内訳を追加した**（`body`も加えた。base64の解析は
ただではない）。クライアントは`vision.serverTiming`として記録する。
`gatewayRoundTrip - total`が残りの正体で、それが回線であることも初めて言えるようになる。

#### 画像縮小の効果は、比較できる組でだけ言える

同じ`bs_usage_events`から`input_units`を取った。**Copilotターンの組が唯一条件の近い比較である。**

| | 候補数 | 画像（base64 KB） | input_units |
|---|---|---|---|
| 15:19 Copilot（縮小前） | 131 | 1,302 | 16,799 |

#### ストリーミングしたリクエストのusageが取りこぼされていた（修正済み）

### 1-m. 画像縮小をメインアクターで走らせてUIを固めた（回帰、2026-08-05・修正済み）

1-iの画像縮小を入れた直後の実機で、**Vision起動が「画面を見ています…」で止まった。**
同時に`NSHostingView is being laid out reentrantly while rendering its SwiftUI content.
This is not supported and the current layout pass will be skipped.`が繰り返し出ていた。

原因は`GatewayVisionClient.encodedImage`である。`VisionSession`は`@MainActor`なので、
そのリクエストTaskはメインアクターを継承する。つまり3380x1892のPNGデコード、再描画、
再エンコード、560KBのbase64化が**パネルを描画しているアクター上で**走っていた。

**遅いだけの問題ではない。** `downscale`は`NSGraphicsContext.current`という**グローバル状態**を
差し替える。それをメインアクターで行うと、SwiftUIが描画中にAppKitの描画コンテキストを
奪うことになる。だからログは「遅い」ではなく「layout passをスキップした」と言っている。

修正は`Task.detached(priority: .userInitiated)`へ移した。`ScreenshotAttachment`ごと渡さず
url／pixelWidth／pixelHeight／captureRectだけを渡し、base64化も内側で行う。

**同時に、ストリーミング表示の更新頻度も直した。** 1ターンは約180増分で届く。その都度
`@Published`を更新し`scrollTo`していたので、1ターンあたり180回のSwiftUI描画と180回の
スクロール指示になっていた。100msごとにまとめて反映する（毎秒10回）形にした。
文字が流れて見える速さは保たれ、負荷は20分の1になる。予定された反映が「本物の回答が
入った後に下書きを復活させる」ことがないよう、結果・撤回・破棄のすべてで
`clearStreamingText()`が保留分とタイマーを落とす。

**教訓は速さの話ではない。** 1-iの縮小自体は測って正しいと確認したが、**どのアクターで
走るかを確認していなかった。** 「何を計算するか」を測っても「どこで計算するか」は測れない。

- **`bs_plans`は何にも依存しない**（`loadPlans`は全行を取る）。`authenticate`の先頭で

- **枠のCOUNTはtenantだけに依存し、上限はplanだけに依存する。** 直列である必要が無いので

### 1-p. 未計測（推測で直さないもの）

- **論理解像度でも開いたメニューの文字が読めるか。** これがR12 E6の合格条件そのものである。
  読めないなら縮小は採らない。判定には**メニューを開いた実画面のスクリーンショット**が必要で、
  probeを起動したシェルには画面収録の許可が無いため取得できていない。
- **回線1,106〜1,798msの内訳。** アップロード（636KB）とTLSと応答転送の比率。
- `gained`の実使用分布（1-cの判断材料）。
- reviewとsuggestを逐次化した場合の効果。

### 1-q. preflightは複数の冷間往復が積み上がっていた（実測・改善、2026-08-06）

冷えた状態で指定どおり1回測った。初回の`sinceAsk`は10,416ms、Gateway往復は8,260msだった。

| getUser | tenant | entitlement | plan | count | auth計 | quota計 | provider | 回線等の差 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **1,099ms** | **665ms** | **639ms** | 0ms | 273ms | 2,405ms | 273ms | 2,799ms | 2,763ms |

どれか1つではなく、冷えた接続上の連続往復が積み上がっていた。質問・Copilotのauthは0msまで
温まった一方、COUNTは642 / 942 / 693msと毎ターン再発した。成功usageの記録後に従来の
boolean cacheを消していたため、次のターンが直前に書いた値をPostgresへ聞き直していた。

正しさと失効意味論を変えず、次を実装した。

- `bs_profiles.default_tenant_id` → `bs_tenants.id` → `bs_entitlements.tenant_id`のFKを確認し、
  profile・tenant・entitlementをPostgRESTのembedded relation 1リクエストへ統合した。DB変更は無い。
  温まったローカル測定でも別々の取得より51〜133ms短く、冷間では639ms相当の往復を1つ消せる
  見込みである。旧クライアント向けtiming fieldは残し、新クライアントは`tenantEntitlement`で記録する。
- 枠cacheを期限だけでなく`used` / `limit`を持つ5分の値cacheへ変えた。成功usageを書いたinstanceは
  既知の`used`をその場で進め、次ターンのCOUNTを0msにする。重複insert時は他instanceとの競合を
  考えて破棄し、次回DBと照合する。keyにはUTC月を含め、月替わりに前月値を持ち越さない。
  無制限planで表示用COUNTを省略した場合は未知値のまま扱う。

残る大きな選択は`getUser=1,099ms`である。Supabaseの`getClaims()`は非対称署名ならJWKSをcacheして
ローカル検証できるが、毎回Authへ問い合わせる`getUser()`よりユーザー削除・明示失効の反映が遅れ得る。
約1.1秒と失効即時性の交換なので、ユーザー判断なしには変えない。

AXの2パス目は今回も3回すべて`gained=0`で、通算10標本中9つが0になった。ただし1標本は76候補を
追加しているため、固定500msをまだ無条件には削らない。

### 1-r. 往復削減は成立。AIだけJWTをローカル検証する（実測・判断、2026-08-06）

初回は`getUser=290ms`、結合後の`tenantEntitlement=244ms`、quota=674ms。後続質問は

|---|---:|---:|---:|---:|---:|---:|

## 2. 不変条件

> **速くするために、正しさを削らない。**
> 増分は読ませるためだけに使う。mode、ハイライト対象、不確実性は必ず最後の検証済み
> オブジェクトから読む。ストリーミングが検証を緩めてはならない。

> **見せた文字は勝手に別の文字へ化けない。**
> 一次モデルが回答途中で落ちた場合、二次モデルの回答を継ぎ足さない。`reset`で明示的に
> 撤回してから書き直す。どちらのモデルも書いていない文章を作らない。

> **待たせている間、何をしているか述べる。**
> 「ローディング中」は情報が無い。画面を見ている／考えている／書いている、を区別する。

## 3. マイルストーン

- **L1（単一起点で測る、完了）** `SummonClock`と`vision.firstContent`。Copilot経路の
  記録追加。AX passの`gained`記録。受け入れ条件: ジェスチャから最初の可読内容までが
  1つの記録から読める。→ 完了（1-a、1-b）。

- **L2（分かった順に出す、実装済み・実機未検証）** VisionのGatewayとクライアントを
  逐次化した。`stream: true`が初めてプロバイダへ届く。`JSONStringFieldStream`が
  未完成のJSONから`message`だけを取り出す。fallback方針は`ai-routing.ts`の
  `runStreamWithModelFallback`に置き、非ストリーミング版と同居させる。
  受け入れ条件: `vision.firstContent`が`via=stream`で`vision.turn`より有意に早いことを
  **実機で**確認する。→ プロバイダ契約は実測済み（1-e）。**本番Gateway経由の実機確認は未了。**

  **安全網:** ストリーミングは最適化であり、最適化が機能そのものを壊してはならない。
  一度も文字を出せずにストリームが失敗した場合は、同じモデルへ従来の非ストリーミング呼び出しを
  行う（`streamVisionModel`）。ユーザーは「遅い回答」を得るのであって「回答なし」にはならない。
  文字を出した後の失敗は退避させない（撤回はmodel fallbackの`reset`の仕事である）。
  退避したことはusage metadataの`stream_degraded`に残す。**黙って退避すると、
  ストリーミングの遅延計測が「実際には走らなかった経路」を説明することになる。**

- **L3（画像コスト、実装済み・実機検証待ち／R12 E6と合流）** 実画面（プルダウンを開いた
  Kinsta）で解像度別の可読性を測り、**論理解像度が1/1と区別できないこと**を確認したうえで、
  Gatewayへ送る画像だけを1ピクセル=1ポイントへ落とした。画像トークン7,756→2,032（3.8分の1）。
  1/3以下では小さい値が壊れ、しかも「読めない」と言わずに幻覚する（1-i）。
  ディスク上の画像と`captureRect`は変えないのでハイライト座標は無影響。
  受け入れ条件: 実機で`vision.image`が論理解像度を示し、`gatewayRoundTrip`が下がり、
  かつ案内の正確さが落ちていないこと。**標本は1画面なので、正確さが落ちたら最初にここを戻す。**

- **L4（AXをどこまで取るか、一部完了）** 「どこから諦めるか」を決める前に、1秒が何に
  使われているかを測った（1-i）。**費用は待ち時間ではなく1ノードあたりの往復回数だった。**
  属性読みを1往復へまとめ（2.3〜5.7倍、候補は同一）、期限は動かさずノード上限を
  2,000→8,000へ上げた。撮影範囲外サブツリーの刈り取りは測定の上で却下した（Xcodeで
  812→2ノード）。→ **実装済み・実機検証待ち。**

  残り: 2パス目の条件（`stillGrowing`が1パス目で必ず真になる）。実使用の`gained`は現時点で
  4標本のうち3つが0、1つが76だった。まとめ読みで1パスが速くなった今、2パス目の500ms待機を
  払う価値があるかは`gained`の分布を見てから決める。
  受け入れ条件: 2パス目を削る／残す判断が1台1セッションではない数字に基づく。

- **L5（Copilotの撮影予算、未着手／R12 E2と合流）** 変化なし判定が8回の試行を使い切る
  経路を、R12 E2の判定見直しと同時に解消する。片方だけ直すと「変化なし」の誤断定か
  5秒の待機のどちらかが残る。

- **L6（review / suggestの逐次化、未着手）** 機構はL2で揃った。reviewは`revised_text`が
  schemaの先頭にあり、そのために先頭へ置かれている。

- **L7（モデル選定、未着手）** R12 E6と同一。**L3・L4・R12 E1〜E5の後**に行う。
  合格の第一ふるいは「開いたプルダウン／メニューの中身を読めること」で、遅延と単価はその次。
