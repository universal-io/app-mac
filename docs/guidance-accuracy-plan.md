# 案内の正確さ（R12）

最終更新: 2026-08-03 ／ ステータス: 計画確定・未着手

進捗と受け入れ条件の正本は[マスタープラン R12](universal-io-master-plan.md)、
本書は原因分析・目標構造・マイルストーンの正本とする。

R11（[reliability-hardening-plan.md](reliability-hardening-plan.md)）が「無音で止まらない」を
扱ったのに対し、本プロジェクトは**動いているのに内容が正しくない**を扱う。

## 0. なぜ

2026-08-03の実機使用で、Copilotが次の状態になった。Kinstaのサイト情報画面でプルダウンを開いた
直後である。

- 画面にはプルダウンが開いて表示されているのに、「操作は検知しましたが、画面に変化は
  見えませんでした」と述べた。
- 同じターンで、ハイライトがボタンではない要素を指した。

同日、先回り文案が相手のメッセージではなく**ユーザー自身の1つ前の発言**へ返信し、相手が実行
済みの操作をユーザーがこれから行う行為として書いた（マスタープラン M0.6）。

どちらも「止まっている」わけではない。動いていて、内容が誤っている。**この状態のまま使うと、
ユーザーは案内を信用できない。** 信用できない案内は無いより悪い。R11の完了だけでは製品にならない。

## 1. 実測

### 1-a. 「変化は見えませんでした」はピクセル差分の判定である

unified logの実測（PID 20271、2026-08-03 21:57）。

```text
21:57:01.366 stable capture attempt=0 phase=change diff=0.0088
21:57:02.082 attempt=1 diff=0.0088
…（8回すべて 0.0088）
21:57:06.106 attempt=7 phase=no_change_adopt
21:57:06.110 progress capture adopted changeObserved=0 settled=1
```

しきい値は`ScreenshotCaptureService.changeBlockThreshold = 0.05`。プルダウンが開いた変化は
**0.0088**、しきい値の約1/6で「変化なし」と判定された。ノイズ床は0.0015なので、変化自体は
検出されている。**しきい値だけの問題ではない。** 比較は48×48へ縮小したうえで12×12ブロックの
最大値を見るため、白い面に白いメニューが重なり文字だけが増える変化は、縮小の時点で消える。
現在の値はGA4サイドバー（blockMax約0.085）を基準に決めており、この画面では効かない。

**この文字列の出所はクライアント内で完結している。** モデルを替えてもこの行は変わらない。
ただしそれは「この障害にモデルが関与していない」という意味ではない（1-d）。同じターンで
起きていたプルダウン内容の不理解と的外れなハイライトはモデル依存であり、そちらの方が重い。

### 1-b. Copilotは構造上、変化を知覚できない

`VisionSession.evaluateCopilotProgress`が送るのは、新しい画面画像、その時点のAX候補、identity、
`goal`、`previousInstruction`である。`turns: []`、`question: nil`で、**前の画面画像を渡していない**。

モデルが見るのは常に「今の画面」1枚だけであり、原理的に「何が変わったか」を答えられない。
それにもかかわらずUIは変化の有無を断定し、プロンプトは前回の指示との関係を語らせている。

### 1-c. AX候補がターンごとに不安定である

同一セッション・同一画面での連続3ターン。

```text
21:56:48  AX visited=648   candidates=136  reason=complete
21:57:06  AX visited=648   candidates=136  reason=complete   ← プルダウン表示中。前ターンと完全同一
21:57:24  AX visited=2000  candidates=0    reason=node_limit ← 候補ゼロ
```

3行目は確定した欠陥である。`Budget.maxNodes = 2_000`に当たって候補が1件も返らず、モデルは
矩形を選べない。ハイライトが的外れになる直接の材料がここにある。**候補ゼロは失敗であるのに、
現在は成功と同じ経路を通り、ユーザーにもログにも区別が出ない。**

2行目の完全一致（648/136）は「開いたプルダウンがAX候補に入っていない」ことを強く示唆するが、
両時点とも開いていた可能性を排除できない。**断定しない。** M1の直接probeで確定させる。

### 1-d. Cerebrasトライアルの終了（2026-08-04）

Vision / Copilotの一次を`gpt-5.6-luna`へ戻した。理由は**開いたプルダウンの中身を読めないこと**
である。

これは一部の画面の問題ではない。GA4、Kinsta、各種管理ツールは、目的の項目がメニューの中に
あって初めて現れる構造をしている。**開いたメニューを読めないなら、案内機能そのものが成立しない。**
到達点が見えていない案内は案内ではない。

リクエストの作り方自体も非対称だった。

| 経路 | 画像の送り方 |
|---|---|
| responses（OpenAI） | `detail: VISION_IMAGE_DETAIL`（`"original"`）を明示する（`vision-engine.ts:305`） |
| chat_completions（Cerebras） | `image_url`のみ。**detail指定が無い**（`vision-engine.ts:353`） |

原寸で読ませる要求を出しているのはresponses経路だけで、chat_completions経路はベンダー既定の
縮小に委ねている。31Bの小型モデルであることも重なる。ただし**Cerebrasが実際にどの解像度で
処理したかは未測定**であり、ここで断定するのはリクエスト形状の非対称までとする。

#### 当初の切り分けの誤り

初版は「『変化は見えませんでした』はクライアントのピクセル差分なのでモデルとは無関係」と
書いた。文字列の出所としては正しいが、**結論の一般化として誤りである。** ユーザーが報告した
のは3つの症状（誤った変化なし表示、プルダウン内容の不理解、的外れなハイライト）で、
そのうち後の2つはモデル依存である。狭い発見を全体の結論として書くと、最も重い問題を
見落とす。1-a〜1-cの計測は有効だが、それが「モデルは無関係」を意味したことは一度も無い。

### 1-e. モデル比較（E6）を先に行ってはならない

1-a〜1-cのとおり、現在モデルへ渡っている入力は「前画面なし」「候補ゼロがあり得る」状態に
ある。この入力で2モデルを比べても、モデルの差ではなく入力の壊れ方を測ることになる。
**入力を直してから比較する。** それまでの一次は`gpt-5.6-luna`とする。

## 2. 不変条件

> **アプリは、自分が観測していないことをユーザーへ述べない。**
> 「変化しなかった」は積極的な観測結果であり、測定が不得手な変化を検出できなかったことと
> 区別しなければならない。不在と不明を混ぜない（R10.5と同じ規則）。

> **モデルには、その判断に必要なものを渡す。**
> 前の画面を渡さずに「何が変わったか」を、候補ゼロで「どこを押すか」を問わない。
> 渡していないものについての回答を、モデルの精度の問題として扱わない。

## 3. マイルストーン

各マイルストーンはコミット境界とする。E1→E2の順は固定する。**入力を直してからモデルを測る。**

- **E1（測定してから直す）** 次を実機probeで確定させる。
  - Chrome上のDOMプルダウン、ネイティブのNSMenu、シートの3種で、開閉前後のAX候補集合が
    どう変わるか（1-cの2行目を確定させる）。
  - 同じ3種で、現在の`differences()`が返す`blockMax`の実値。
  - `node_limit`に当たる画面の頻度と、その時に何が失われるか。
  受け入れ条件: 3種それぞれの実測値が本書へ残る。**推定値を根拠に何も直さない。**

- **E2（観測できないことを述べない）** 変化判定を次のいずれかにする。E1の実測で選ぶ。
  - 判定を改善する（縮小率・ブロック粒度・比較領域をハイライト対象の周辺へ絞る等）。
  - 判定を改善できない範囲については、**「変化なし」と述べるのをやめる**。撮影のタイミング
    合わせという本来の役割（`StableScreenCaptureResult`のコメントどおり）に戻し、ユーザーへの
    断定はやめる。
  受け入れ条件: プルダウン、タブ切替、モーダル、トースト、スクロールで誤った「変化なし」が
  出ない。出せない場合は、その状況で何も述べない。

- **E3（Copilotに前後を渡す）** 進捗ターンへ、前の画面と前回の指示を対にして渡す。
  現在`turns: []`で送っている履歴の扱いも合わせて決める。何を渡すかを決めた上で、
  プロンプトに「何が変わったか」を答えさせる。
  受け入れ条件: プルダウンを開いた直後のターンで、モデルが「メニューが開いた」を根拠として
  次の一手を述べる。渡す情報が増える分の遅延とトークンを実測して記録する。

- **E4（候補ゼロを失敗として扱う）** `node_limit`で候補が空になったターンを成功と同じ経路に
  流さない。診断（R11の`Diagnostics`）へ`truncatedReason`と候補数を記録し、ハイライトを
  出せないことをユーザーへ示すか、収集方法を変える。Copilot進捗ターンは現在R11の
  `vision.request`／`vision.turn`を出していないため、まずここを記録対象に含める。
  受け入れ条件: 候補ゼロのターンが動作記録から識別できる。矩形の無い案内は矩形があるふりを
  しない。

- **E5（話者と実行者）** マスタープラン M0.6。先回り文案が相手の最新メッセージではなく
  ユーザー自身の発言へ返信し、実行者を反転させる。規則も構造化認識フィールドも既にあるため、
  **なぜ既存の規則が適用されないかの特定から始める**。文案下の「認識:」行（`groundingNote`）が
  そのまま証拠になる。
  受け入れ条件: AIチャット画面、Slack、Gmailで、`latest_message_sender`と
  `requested_action_owner`が実画面と一致する。長い相手メッセージでも成立する。

- **E6（固定材料での比較）** E1〜E5の後に、同じ画面・同じ質問の固定材料で候補モデルを
  比較し、一次モデルを決める。現在の一次は`gpt-5.6-luna`（1-d）。
  **合格条件に「開いたプルダウン／メニューの中身を読めること」を必ず含める。** これが読めない
  モデルは、遅延と単価がどれだけ優れていても案内には使えない。安いモデルを試すこと自体は
  正しいが、次に試すときはこの1点を最初のふるいにする。
  chat_completions経路へ`detail`相当の指定を送れるかも、比較の前に確認する。
  受け入れ条件: 案内の正しさ、矩形選択の正しさ、メニュー内テキストの可読性、遅延、単価を
  同じ材料で比較した表が残る。正本は`ai-routing.ts`のまま動かさない。

## 4. 対象外

- R11の残作業（長時間稼働試験）。独立して進める。
- Skills／ツール個別の精度（R8 M7カタログ基盤）。本プロジェクトは汎用経路の正確さを扱う。
- 新しいsurface、endpoint、model routeの追加。

## 5. 検証

- 実機probe（E1）。リポジトリ外の短命probeで行い、常設の代替経路を作らない。
- macOS unit test（判定ロジックとプロンプト組み立てはtestで固定できる範囲を固定する）。
- 署名なしDebug build、webのlint／型検査／production build。
- 実画面での確認。**この種の欠陥は自動テストでは見つからない。** 発見はすべて実使用から来た。
