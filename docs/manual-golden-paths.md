# 手動ゴールデンパス検証チェックリスト

作成: 2026-07-12 ／ ステータス: 土台作り直し（シャーシ交換方式）Phase 0 成果物

## 使い方

このドキュメントは、基盤の作り直し（リファクタリング）を進める中で
**「何が壊れたかを人間の目で即座に検知する」**ための全機能シナリオ集。

- コードからの自動テストではない。実機で手を動かして確認する。
- **フェーズ完了ごと（大きな変更をマージする前・リリース前）に全シナリオを実施**し、
  下の結果記録表に ✅ / ❌ / ⚠️（一部不具合）を記録する。
- ❌ が出たら、そのフェーズの変更が原因かどうかを切り分けてから次に進む。
- 「壊れやすさ」注記があるシナリオは過去に実際に壊れた・タイミング依存で不安定だった
  箇所。特に注意して確認する。
- 期待結果は「観察可能な事実」で書く（内部状態ではなく画面・音・挙動）。
- 各シナリオの前提はできるだけ独立させているが、GP-01 → GP-02 のように直前のシナリオの
  状態を引き継ぐ場合はその旨を明記する。

## GP-01: メニューバー常駐・Dockなし

**前提**: アプリがビルド・署名済み（Debug は Apple Development 証明書。ad-hoc 署名は禁止）。

**操作手順**:
1. アプリを起動する。
2. Dock を目視確認する。
3. メニューバー右側を確認する。
4. `⌘Tab` でアプリ切り替えリストを開く。

**期待結果**:
- Dock にアイコンが出現しない（`NSApp.setActivationPolicy(.accessory)`）。
- メニューバーにアイコンが常駐している。
- `⌘Tab` の切り替えリストにも出現しない（accessory ポリシーのため）。

**壊れやすさ**: `applicationDidFinishLaunching` の `terminateOtherRunningCopies()` が旧ビルドを
kill する。Xcode の DerivedData に古いプロセスが残っていると、右Shift ジェスチャが2重に反応する
（2つの MenuBarExtra が出る、ジェスチャが1回で2回分反応する等）。起動後に Activity Monitor で
プロセスが1つだけであることを確認するとよい。

## GP-02: 起動直後の右Shift2回が効くこと

**前提**: GP-01 完了直後（アプリ起動直後、まだ一度もパネルを開いていない）。アクセシビリティ権限は
付与済み。

**操作手順**:
1. 任意のアプリ（例: メモ.app）を前面にする。
2. 右Shift を素早く2回タップする。

**期待結果**:
- パネルが画面中央に出現し、原文欄に自動フォーカスされる。
- 待機時間なく初回から反応する（起動直後で `ShiftGestureMonitor` や `HotKeyCenter` の初期化が
  遅延している場合、1回目のジェスチャが無視されることがある）。

**壊れやすさ**: `gesture.start()` と `HotKeyCenter.shared.register()` はいずれも
`applicationDidFinishLaunching` 内の非同期初期化に依存する。起動直後の数百ms以内に操作すると
ジェスチャモニタがまだ準備できておらず反応しないことがある。数秒待ってから再試行して切り分ける。

## GP-03: compose — 召喚→入力→レビュー（SSEストリーミング表示）

**前提**: ログイン済み。パネルは閉じている。

**操作手順**:
1. 任意のアプリを前面にして原文欄が空の状態でパネルが出ないことを確認（閉じている）。
2. 右Shift2回でパネルを召喚する。
3. 原文欄に「これはテストです、至急対応してください、バカじゃないの」など攻撃的な文を入力する。
4. 原文欄にフォーカスがある状態で右Shift2回を押す（レビュー実行）。

**期待結果**:
- レビューが開始され、結果ペインにモデル名の表示が出る。
- クラウド経由（I//O Cloud）の場合、修正文が**トークン単位でストリーミング表示**される
  （一度に全文が出るのではなく、逐次追加されていくのが目視できる）。
- 完了後、結果右上に使用モデル名と処理時間（ms）が表示される。
- 誤字脱字／失礼・攻撃的表現／分かりにくさの3観点の指摘（issues）が表示される。

**壊れやすさ**: ストリーミング表示は SSE 依存。Gateway 向き先が誤っている（GP-25 参照）とストリームが
一切出ず、いきなり完成形かエラーになる。ネットワーク遅延時に「ローディングのまま止まる」ことがないか
確認する。

---

## GP-04: compose — レビュー結果側の送信（⌘V注入）

**前提**: GP-03 でレビュー結果が表示済み。

**操作手順**:
1. 右Shift1回で結果ペインにフォーカスを移す（または結果側の送信ボタンをクリック）。
2. 結果側の送信ボタン（紙飛行機）をクリックする、または結果ペインにフォーカスした状態で Enter。
3. 呼び出し元アプリ（手順1で前面にしていたアプリ）を確認する。

**期待結果**:
- パネルが閉じる。
- 呼び出し元アプリの元のフィールドに、レビュー結果の文章が自動入力される（合成 ⌘V）。
- 入力後、送信トースト（`didDeploy`）などの成功フィードバックがある。

**壊れやすさ**: 合成ペーストは遅延ベースで100%保証ではない。重いアプリ（Electron製など）で
取りこぼすことがある。ターゲットアプリがフォーカスを失っている場合に注入が空振りしないか確認。

---

## GP-05: compose — 原文側の送信（レビューなし）

**前提**: パネルが開いており原文欄に文章がある（レビュー未実施でも可）。

**操作手順**:
1. 原文欄にフォーカスがある状態で、原文側の送信ボタン（紙飛行機）をクリックする、または Enter。

**期待結果**:
- レビューを経由せず、原文欄の文章がそのまま呼び出し元フィールドへ注入される。
- パネルが閉じる。

**壊れやすさ**: 特になし（比較的安定した経路）。ただしレビュー中（isLoading）に誤って原文送信が
できてしまわないか確認する。

---

## GP-06: compose — 履歴5件表示・クリック送信

**前提**: 過去に何件か送信履歴がある状態（ローカル履歴 ON）。原文欄が空。

**操作手順**:
1. 右Shift2回でパネルを召喚する（原文欄は空）。
2. パネル下部を確認する。
3. 履歴の中の1件をクリックする。

**期待結果**:
- 原文欄が空の状態で、下部に最近の送信履歴が最大5件表示される。
- 履歴の1件をクリックすると、その文面がそのまま（レビューを経ずに）呼び出し元へ送信される。

**壊れやすさ**: 履歴が0件・1件・5件超のケースで表示崩れがないか確認。`isLoadingRecentHistory` の
ローディング状態が一瞬でも見えるか、フリーズしないかも確認。

---

## GP-07: 右Shift1回でフォーカス切替

**前提**: パネルが開いており、原文欄と結果欄の両方にテキストがある（レビュー実施済み）。

**操作手順**:
1. 原文欄にフォーカスがある状態で右Shift1回タップ。
2. 続けてもう一度右Shift1回タップ。

**期待結果**:
- 1回目のタップで結果欄へフォーカスが移り、青いフォーカスリングが結果欄側に移動する。
- 2回目のタップで原文欄へフォーカスが戻る。
- レビュー結果がまだない（片側しかない）状態では、フォーカスリング自体が出ない、または切替が
  無視される（`canFocusRevision` が false の場合の仕様）。

**壊れやすさ**: `canToggleEditorFocus` が false のケース（Vision/Navigator/Copilot 中など
テキスト2ペインでない状態）で誤動作しないか確認。

---

## GP-08: Enter送信 / Shift+Enter改行

**前提**: パネルが開いており原文欄にフォーカスがある。

**操作手順**:
1. 原文欄に1行目を入力し、Shift+Enter を押す。
2. 続けて2行目を入力する。
3. 通常の Enter を押す。

**期待結果**:
- Shift+Enter では改行が挿入され、送信は発生しない（パネルは開いたまま）。
- 通常の Enter では、カーソルがある側（この場合は原文）がそのまま送信され、パネルが閉じる。
- IME（日本語入力）変換中に Enter を押した場合は変換確定のみで送信されない（IME確定後の
  Enter で初めて送信される）。

**壊れやすさ**: IME変換中の Enter が誤って送信をトリガーしないか（日本語入力の確定タイミングと
送信ショートカットの競合は再発しやすいバグ）。

---

## GP-09: esc・右Shift2回でパネルを閉じる

**前提**: パネルが開いている（compose の任意の状態）。

**操作手順**:
1. パネルが開いている状態で esc キーを押す。
2. 再度右Shift2回でパネルを召喚する。
3. 今度は右Shift2回（原文欄にフォーカスがない状態、または結果欄にフォーカスがある状態）で
   閉じられるかを確認する。

**期待結果**:
- esc でパネルが即座に閉じる（`KeyablePanel.onCloseRequested`）。
- 結果欄にフォーカスがある状態で右Shift2回をしても**何も起きない**（README仕様: 「レビュー結果欄では
  何もしない」）。パネルを閉じるには esc または原文欄にフォーカスを戻してから、の挙動を確認。

**壊れやすさ**: `advance()` 内の分岐（`shouldClosePanelOnHotkeyDoubleTap` / `focusedField == .draft`
ガード）はモード（compose/transform/vision/navigator/copilot）ごとに閉じる条件が異なる。各モードで
同じ操作をしても閉じ方が違うことがあるため、モードを変えて再確認する価値がある。

## GP-10: ASR — 右Shift長押しで録音→文字起こし挿入

**前提**: パネルが開いており原文欄にフォーカス可能。マイク権限付与済み。

**操作手順**:
1. 右Shift を押し続ける（長押し）。
2. 「開始」の効果音を確認し、赤いマイクインジケータ（録音中UI）を確認する。
3. 2〜3秒何か話す。
4. 右Shift を離す。
5. 「終了」の効果音を確認する。

**期待結果**:
- 押した瞬間に効果音（開始 cue）が鳴り、録音中インジケータが表示される。
- 離すと効果音（終了 cue）が鳴り、しばらくして文字起こし結果が原文欄に挿入される
  （`isTranscribing` 中はローディング表示）。
- 極端に短い（0.4秒未満）または無音に近い録音は無視され、文字起こしされない（silence gate）。
- エディタ以外（例: navigator の質問入力欄が無い bare vision 状態）でロング押ししても録音が
  始まらない、または安全に無視される。

**壊れやすさ**: `isDictating` の二重発火ガード。長押し中にパネルが閉じられる、または他の
ジェスチャと同時発火した場合の挙動。無音判定の閾値（duration < 0.4 or averagePower < -45）は
環境（マイク音量設定）依存で誤判定しやすい。

## GP-11: transform（受信）— 選択テキスト取り込み→自動変換

**前提**: パネルは閉じている。Slack や Mail など任意のアプリに、相手からの攻撃的・分かりにくい
メッセージが表示されている。

**操作手順**:
1. 対象アプリで相手のメッセージをマウスでドラッグ選択（反転表示）する。
2. 右Shift2回を押す。

**期待結果**:
- 選択テキストが ⌘C 合成で取り込まれ、原文ペインに自動的に入る。
- **第2のジェスチャ不要**で自動的に変換（transform）が走り、処理中は右ペインにスピナーが出る。
- 完了すると右ペインに「状況 → 求められていること → 提案アクション（返信文案）→ 整理した内容
  （攻撃性・感情・皮肉を除いた中立版）」が表示される。

**壊れやすさ**: 選択が無い状態と誤判定して compose モードに落ちる、または逆に選択が無いのに
古いクリップボード内容を誤って取り込むことがないか（`SelectionGrabber` のタイミング競合）。
コピー系ショートカットを奪う他の常駐ツール（クリップボード管理ツール等）との干渉も要確認。

---

## GP-12: transform — 出口はコピーのみ・書き戻さない

**前提**: GP-11 完了直後、右ペインに整理結果が表示されている。

**操作手順**:
1. 「コピー」ボタン、または提案アクションの「承認してコピー」をクリックする。
2. 元のアプリ（Slack/Mail 等）の入力欄・元のメッセージ欄を確認する。
3. どこか別のテキストフィールドに ⌘V で貼り付けてみる。

**期待結果**:
- 元のメッセージ・元のアプリのどのフィールドにも一切書き戻されない（`ClipboardDeployer` のみ）。
- クリップボードにコピーされた内容を別の場所へ ⌘V すると、整理済みの文面が貼り付けられる。

**壊れやすさ**: `makeDeployer(for:)` の分岐で mode が誤って `.compose` として扱われると
`PasteDeployer` が使われ、書き戻し禁止の原則が破られる重大リグレッションになるため必ず確認する。

## GP-13: クリップボード退避・復元

**前提**: 事前に、意味のあるテキスト（例: 「元々コピーしていた内容ABC123」）を手動でコピーしておく
（クリップボードに乗せておく）。

**操作手順**:
1. 上記のテキストをコピーする（⌘C）。
2. compose フローで何かレビュー結果を送信する（GP-04 の操作、⌘V 注入が発生する）。
3. 送信完了後、別のテキストフィールドで ⌘V を押す。

**期待結果**:
- ⌘V で貼り付けられる内容が、手順1でコピーした「元々コピーしていた内容ABC123」に**復元されている**
  （送信時に一時的に借りたクリップボードが、処理後に元の内容へ戻っている）。

**壊れやすさ**: README に明記の通り「退避・復元も合成ペースト／コピーも遅延ベースのため原理的に
100%完全ではない」。重いアプリでの取りこぼし、他のクリップボード管理ツール（Alfred/Raycast等）との
併用時に復元が失敗するケースがある。複数回連続で送信した場合に復元が崩れないかも確認する。

---

## GP-14: Vision — 空欄で右Shift2回→選択オーバーレイ→Enter確定

**前提**: パネルが開いており原文欄が空。画面収録権限が付与済み。

**操作手順**:
1. 原文欄が空の状態で右Shift2回を押す。
2. 画面に選択オーバーレイが出現することを確認する。
3. **何もドラッグせず** Enter を押す。

**期待結果**:
- テキスト入力を閉じる代わりに Vision モードへ入り、選択オーバーレイが開く。
- **最初から全画面（カーソルのあるディスプレイ）が選択された状態**になっている。
- Enter を押すと、ドラッグなしでそのまま全画面がキャプチャされ（ScreenCaptureKit）、Vision の
  解釈UIへ遷移する。

**壊れやすさ**: マルチディスプレイ環境で「カーソルのあるディスプレイ」の判定がずれることがある
（`NSScreen.screens.first { $0.frame.contains(mouse) }`）。ScreenCaptureKit が失敗した場合のみ
`screencapture -i` にフォールバックする経路も、権限が中途半端な状態で挙動が変わりやすい。

---

## GP-15: Vision — ドラッグ範囲選択・escで戻る

**前提**: GP-14 と同じ前提（選択オーバーレイが出せる状態）。

**操作手順**:
1. 原文欄が空の状態で右Shift2回を押し、選択オーバーレイを出す。
2. 画面の一部をドラッグして範囲選択する。
3. マウスを離す前に esc を押す。
4. 再度右Shift2回でオーバーレイを出し、今度は正しくドラッグして範囲を確定する。

**期待結果**:
- 手順3: esc でパネルへ戻る（Vision セッションは破棄されずパネルの待機状態に戻る、または
  原文入力状態に戻る）。
- 手順4: ドラッグで指定した範囲だけがキャプチャされる（全画面ではなく指定範囲）。

**壊れやすさ**: esc と右Shift2回でオーバーレイからの離脱の意味が違う（README: 「esc でパネルへ戻り、
右Shift2回ならセッションごと破棄して待機モードへ」）。この2つの挙動差が実装で入れ替わっていないか
要確認。

---

## GP-16: Vision — 解釈結果と「承認して送信」「編集する」

**前提**: GP-14 の続き。全画面または範囲キャプチャが完了し、Vision 解釈UIが表示されている
（フォーム画面や質問が写ったスクリーンショットが望ましい）。

**操作手順**:
1. 解釈結果（状況 → 求められていること → 提案アクション → 読み取った内容）が表示されるのを待つ。
2. 提案アクションのうち文案付きのもの（`reply` など）を1つ選ぶ。
3. 「承認して送信」を押す（1回目の検証）。別セッションで同じところまで進め、今度は「編集する」を
   押す（2回目の検証）。

**期待結果**:
- 左にスクリーンショット、右に「状況→求められていること→提案アクション→読み取った内容」の4項目が
  表示される。提案アクションは最大3件。
- 「承認して送信」: そのまま呼び出し元フィールドへ注入（⌘V合成）され、パネルが閉じる。
- 「編集する」: 原文エディタへ文案が引き継がれ、ユーザーが編集できる状態になる（送信されない）。

**壊れやすさ**: 提案アクションが0件（`info_only` のみ）の場合にボタン列が崩れないか。
Persona/Relationship カード（メモリ機能, GP-23）が有効な場合と無効な場合で文案の質が変わるのは
仕様通りだが、メモリ未設定でもエラーにならず動作すること。

## GP-17: Navigator — マルチターン質問とハイライト

**前提**: Vision で何らかの画面（例: 分析ツールやフォームのスクリーンショット）を解釈済み、
または Navigator/Copilot 経路の設定が ON（設定 → 「スクリーンショットを Navigator / Copilot 経路で
扱う」）。

**操作手順**:
1. Vision 解釈結果の下にある質問入力欄に、画面内の要素について質問する（例:「保存ボタンはどこ？」）。
2. Enter で送信する。
3. 回答が返ってきたら、続けて別の質問を入力しもう一度送信する（2ターン目）。

**期待結果**:
- 1ターン目の回答がストリーミング表示され、対象要素が実画面上またはパネル内プレビュー上で
  ハイライト（赤枠）される。
- 2ターン目も会話履歴を踏まえた回答が返る（マルチターンの文脈保持）。
- 画面内に対象が見えている質問には、なるべく毎回ハイライトが付く
  （navigator-copilot-plan.md の Phase 1 で修正済みの想定挙動）。

**壊れやすさ**: `docs/navigator-copilot-plan.md` に記載の通り、フォローアップターンでマーカーが
出ない/誤った要素にハイライトが付く既知の精度課題がある（重複ラベルの誤特定など）。完全一致しない
ことがあっても「機能自体が動くか」を優先して確認し、精度の粗さは記録に留める。

## GP-18: Navigator→Copilot — タスクプラン開始とコーナーストリップ

**前提**: GP-17 の続き。「このタスクを進める」に該当する質問（例:「◯◯の数値を確認する手順を教えて」）
をしてプランナーが「ナビゲーション開始（Nステップ）」ボタンを提示している状態。

**操作手順**:
1. 「ナビゲーション開始」ボタンをクリックする。
2. パネルの見た目の変化を確認する。
3. 画面上でハイライトされた場所を実際にクリックする。
4. パネルの外（ハイライト対象以外）をクリックしてみる。

**期待結果**:
- 開始を押すと、中央の大パネルが**画面右下の小さな帯（コーナーストリップ）**に変形する
  （「ステップ x/y・目的・現在の指示・終了ボタン」のみ表示）。
- 現在のステップ対象が実画面上で赤くハイライトされ、次のステップに進むまで**消えない**。
- ハイライトされた場所をクリックすると、自動でスクリーンショットが撮り直され、進捗が確認され、
  進んでいれば次のステップ（x+1/y）へ自動的に進む。
- **パネルの外をクリックしてもコパイロットモードが終了しない**（`handleResignActive` が
  copilot 中は無効化されている）。これは意図的な仕様。

**壊れやすさ**: `docs/navigator-copilot-plan.md` の直接原因として記録された「パネル復帰
（`handleResignActive` → `closePanel`）」問題がコパイロット導入で迂回された経緯がある。
`AppDelegate.handleResignActive()` の `guard ... != .copilot` 分岐が壊れると、外クリックのたびに
パネルが閉じてコパイロットが機能しなくなる重大リグレッションになるため必ず確認する。
再スキャン判定は暫定実装（OCR joinedText が前回と同じなら1回だけ再取得）のため、画面が変化したのに
「変化なし」と判定されるケースがある（`docs/navigator-stabilization-followups.md`）。

## GP-19: Copilot — 終了

**前提**: GP-18 でコパイロットモード中（コーナーストリップが表示されている）。

**操作手順**:
1. 帯の「終了」ボタンをクリックする（または右Shift2回）。
2. 最終ステップまで自然に完了させた場合の挙動も別途確認する（最後のステップで目的の答えが
   読み上げられる想定）。

**期待結果**:
- 「終了」または右Shift2回でいつでもコパイロットを離脱できる。
- 離脱すると通常の広いパネルレイアウトに戻る。
- 最終ステップ完了時は、案内ではなく目的の答え（例:「mobile は◯◯件、△△%です」）が示され、
  通常パネルに戻って結果が見える。

**壊れやすさ**: `docs/navigator-stabilization-followups.md` に明記の既知の弱点:
「copilot の終了状態が弱い。完了、停滞、再確認待ちを明示する終端状態が未実装」「案内完了時の
自動クローズか完了表示+閉じる導線かが未定」。**現状は完了しても自動で閉じない/完了表示が
弱い可能性がある**——ここでは「現状の挙動をそのまま記録する」ことが目的であり、必ずしも
理想形との一致を求めない。

## GP-20: 出力言語設定の反映

**前提**: 管理ウィンドウの設定タブを開ける状態。

**操作手順**:
1. 管理ウィンドウ → 設定 → 「結果の言語」を日本語→English に変更する。
2. 管理ウィンドウを閉じ、右Shift2回でパネルを新規に召喚する。
3. 英語以外（例: 日本語）の原文を入力してレビューを実行する。
4. 結果を確認したのち、設定を再度日本語に戻し、同様に確認する。

**期待結果**:
- 設定変更は即座に UserDefaults に永続化される。
- 「次にパネルを開いた時から反映される」（既に開いているパネルには反映されない仕様）ため、
  一度パネルを閉じて開き直した後の `revised_text` が選択言語になる。
- `issues` の説明や `summary` は選択言語によらず日本語のまま。

**壊れやすさ**: 「パネルを開くたび日本語に戻る」バグは M3-C で修正済みとされているため、設定した
言語がセッションをまたいで保持されているかが回帰確認のポイント。

## GP-21: L1コンテクストチップの表示・除外

**前提**: 設定で「呼び出し時に画面の文脈を読み取る」が ON。何らかのアプリ（例: メールの返信画面）を
前面にしている。

**操作手順**:
1. 対象アプリで右Shift2回を押しパネルを召喚する。
2. 原文欄上部にチップが表示されるか確認する。
3. チップの除外ボタン（×等）をクリックする。
4. その状態でレビューを実行する。

**期待結果**:
- 召喚直後、原文欄の上に L1 コンテクストチップ（前面アプリ・周辺の会話テキストを要約したもの）が
  表示される。
- チップをクリックして除外すると、チップが消え、以降のレビューにはこのセッションの文脈が
  注入されない（`isContextExcluded`）。
- 文脈読み取りの内容はどこにも保存されない（README仕様）。

**壊れやすさ**: 設定が OFF の場合はチップ自体が出ないことも確認（チップの有無が設定と一致して
いるか）。AXツリーが取得できないアプリ（一部のサンドボックスアプリ等）でチップ生成が失敗して

## GP-22: 管理ウィンドウ — アカウント ログイン/ログアウト

**前提**: 一度ログアウトした状態から開始。

**操作手順**:
1. メニューバーアイコンから管理ウィンドウを開き、アカウントタブを表示する。
2. 「Google 認証」でログインする（ブラウザに遷移→戻る）。
3. ログイン後、アカウント情報（メールアドレス等）が表示されることを確認する。
4. 「ログアウト」ボタンをクリックする。
5. 続けてメールリンク認証も試す: メールアドレスを入力し「ログイン用リンクを送信」→ 受信した
   メール本文のリンクをこの Mac で開く。

**期待結果**:
- Google 認証でブラウザへ遷移している間、パネルや認証待ち画面が勝手に閉じない
  （README: 「Google 認証やメールリンク認証の途中だけは、ブラウザやメールへ移動してもログイン
  画面を閉じない」）。
- ログイン成功後、アカウント情報が正しく表示される。
- ログアウトすると即座に未ログイン状態のUIに戻る。
- メールリンク認証はコード入力ではなく、メール本文のリンクをこの Mac で開く方式で完了する
  （`{{ .ConfirmationURL }}` 前提）。

**壊れやすさ**: `handleResignActive` の「auth.currentSession() == nil の間は resign を無視しない
（＝閉じない）」ガードは、ログイン处理中にブラウザへ切り替えた際にパネル/認証ウィンドウが

## GP-23: 管理ウィンドウ — メモリ（bootstrap・編集・削除）

**前提**: ログイン済み。メモリ機能 ON（設定 → 「スタイルプロファイルを反映・学習する」）。

**操作手順**:
1. 管理ウィンドウ → メモリタブを開く。
2. bootstrap 用のテキストエリアに、自分の過去の文章サンプルを50文字以上貼り付ける。
3. 「ブートストラップ生成」を実行する。
4. 生成された Persona カードの内容を確認し、手動で少し編集して保存する。
5. カードを1件削除する。

**期待結果**:
- サンプルが50文字未満だとヒント文が表示され、生成ボタンが無効/警告される
  （`bootstrapMinimumLength = 50`）。
- 50文字以上で生成を実行すると、Persona カードが作られ一覧に表示される。
- 編集して保存すると内容が更新される。
- 削除すると一覧から消える（`deleteCard` / `deletePersona`）。

**壊れやすさ**: Gateway 未接続・未ログイン状態でメモリ機能を叩くとエラーにならず適切に
無効化されているか（README: 「no-op until the gateway is configured and the user is signed in」）。
`MemorySyncService` のデバウンス同期がローカル編集直後に競合して上書きされないか。

## GP-24: 管理ウィンドウ — 履歴・設定

**前提**: compose/transform でいくつか送信履歴が作られている状態。

**操作手順**:
1. 管理ウィンドウ → 履歴タブを開く。
2. 一覧に最終的に注入した文章が表示されているか確認する。
3. 設定タブで「ローカル履歴を保存」を OFF にする。
4. compose で1件送信し、履歴タブを再度確認する。
5. 設定を ON に戻す。

**期待結果**:
- 履歴一覧には「最終的に注入した文章」だけが表示される（レビュー途中の下書きは出ない）。
- 既定 ON・最新100件までの保存上限が守られている。
- OFF にした状態で送信しても新規履歴が追加されない。

**壊れやすさ**: 履歴 OFF → ON の切り替え直後に、OFF中に発生した送信が後から紛れ込んで記録
されないか（SQLite書き込みタイミングの競合）。

## GP-25: Gateway向き先警告バー

**前提**: `BombSquad.local.plist` の `BOMB_SQUAD_API_BASE_URL` を一時的に
`http://localhost:3000/api` に設定してビルド（ローカル Gateway 開発向け設定）。

**操作手順**:
1. 上記設定でアプリを起動し、パネルを開く。
2. パネル上部を確認する。
3. `BombSquad.local.plist` の値を空に戻し、再ビルド・再起動してパネルを開く。

**期待結果**:
- localhost 等、本番既定（`https://api.universal-io.com`）以外を向いている間は、パネル上部に
  **オレンジの警告バー**（現在の向き先URL付き）が表示される。
- 本番向き（既定値）に戻すと警告バーは表示されない。

**壊れやすさ**: README で「リリース注意」として明記されている通り、`BombSquad.local.plist` は
アプリバンドルに同梱され最優先で読まれる。**配布ビルド作成前にこの値を空に戻し忘れると、
本番ユーザーが誤ってローカルGatewayを向いてしまう**——これがこの警告バーの存在意義そのもの。
`release.sh` がビルド中だけ自動で空にし、ビルド後に復元する仕組みになっているため、
`tools/release.sh` を経由しない手動ビルドでの配布は特に注意。

## GP-26: 管理ウィンドウを開いたままパネル操作（既知バグ記録）

**前提**: 管理ウィンドウが開いている状態。

**操作手順**:
1. 管理ウィンドウを開いたまま、任意のアプリで右Shift2回を押しパネルを召喚する。
2. パネルと管理ウィンドウ、どちらがキーウィンドウ（フォーカス）を持っているか確認する。
3. パネル内でテキスト入力・レビューなど一連の操作をしてみる。

**期待結果（現状の挙動を記録する。理想形との一致は求めない）**:
- `showManagementWindow()` の実装上、パネルを開こうとすると管理ウィンドウ自体は閉じない設計だが、
  `showManagementWindow()` 内では「パネルが開いていれば閉じてから管理ウィンドウを開く」という
  片方向の制御になっている（管理ウィンドウ→パネルの逆方向は未検証）。
- 実際にどちらのウィンドウがフォーカスを奪うか、パネル操作中に管理ウィンドウが前面に出てくる等の
  意図しない奪い合いが起きないかを記録する。
- これは README の設計方針
  「入力補助のたびに管理ウィンドウへ勝手にフォーカスを移さない」に対する既知の弱点候補であり、
  Phase 0 時点では**修正せず、現状の挙動をそのまま記録することが目的**。

**壊れやすさ**: フォーカス管理はウィンドウレベル（`NSApp.activate` / `makeKeyAndOrderFront`）の
競合が起きやすい箇所。将来の基盤作り直しでウィンドウ管理を触った際、この挙動が「改善したか」
「別の形で悪化したか」を比較する基準として使う。
