# レビュー依頼: Vision バブルの配置ロジック

作成: 2026-09-01 ／ 更新: 2026-09-02 ／ 対象: `app-mac`（macOS クライアント）＋ `api-gateway`

**ステータス: レビュー完了、クライアント側の決定を実装。** 根本原因は「1ターン1配置が状態として
存在しないこと」。`resolving → committed → contentVisible`を1箇所に置き、AXヒット無しのターンだけ
最終枠まで本文をバッファする。AX実測・囲みは送信前に配置確定するので速度は変えない。

この文書の初版には2つ誤りがあった。

1. 初版の案C（`targetCandidateId`を先に流す）は、候補0件では矩形へ変換できないため機能しない。
   早期配置に価値があるのは候補idではなく矩形`subjectPlacement`であり、Gateway最適化は実測後へ送る。
2. 「本文・画像・グラフなら`candidates=0`が正常」は過剰一般化だった。candidateは画面全体の操作要素数。
   `collectorEmpty / pointMiss / measured`を分けて記録し、0件は収集側の問題候補として扱う。

Gatewayと公開中の`0.2.2`は変更しない。`AXUIElementCopyElementAtPosition`も、入力位置に応じて値が
変わるか、画面大要素を返さないかを短命probeで測るまでは本実装へ入れない。

**依頼内容**: この1機能の配置ロジックを、設計からレビューしてほしい。対症療法を4回重ねた結果、
規則が正しい形になっていない可能性が高い。「今のコードをどう直すか」ではなく、
**「ユーザーにとって自然な挙動は何で、そのためにどういう構造であるべきか」**から見てほしい。

---

## 1. 前提（30秒）

macOS アプリ「Universal I/O」の Vision という機能。

- 右Shift 2回で、**実画面の上に紫の半透明の覆い（幕）**が乗る
- 幕の上をクリックすると、**その場所について解説する**
- 解説は **バブル**（幅380ptのカード。1つだけ）に出る
- バブルは「指した対象の隣」に置きたい。画面の隅に固定すると、対象とテキストの間で目が往復するため

登場する要素:

| 呼び名 | 何か |
|---|---|
| **リング** | クリックした場所に出る丸。「クリックを受け取った」の合図 |
| **枠** | 対象を囲む四角。AXが実測した要素、または回答が指した対象 |
| **バブル** | 解説と入力欄を持つカード。製品が喋る唯一の場所 |

---

## 2. ユーザー（オーナー）が求めている挙動

原文に近い形で:

1. Vision が始まると、バブルは**画面の右下**にある
2. どこかをクリックすると**リング**が出る。**この時点でバブルは動かない**
3. リングをヒントに、**実際に何を解説するかの枠が確定する**
4. **枠が確定したら、枠が表示され、バブルもその隣に移動する**（右下から）
5. 解説はその後で届くので、しばらくは枠の隣で「考え中」でよい
6. **「リングの隣にバブルが駆けつける」仕様はやめる** — リングは位置が確定していないため

決定的な要求は **「文章が出る前に位置が確定する」**。

> 解説が始まるまでにLLMのタイムラグがあるが、LLMに情報を送っているということは、
> すでに自分がどこに行けばいいか分かっている段階のはずだ

## 3. 現在の実装

### 3.1 1クリックの処理順序

`SessionCoordinator.point(at:session:)`（`BombSquad/Core/SessionCoordinator.swift:1329`）

| # | 処理 | 実測時間 |
|---|---|---|
| 1 | `pointingOverlay.showRing(at:)` — リングを描く。**バブルは動かさない** | 0ms |
| 2 | `session.beginPointing()` — 前の回答を捨て「ここを読んでいます…」にする | 0ms |
| 3 | スクリーンショットを撮り直す（クリック時点の画面） | 〜200ms |
| 4 | AXツリーを歩いて候補を集める（操作系13ロールのみ） | 〜100ms |
| 5 | `VisionPointerResolver.candidate(at:)` で、指した座標の下の候補を引く | 〜0ms |
| 6 | `setMark(point:frame:)` — **枠が取れた時だけ**バブルを移動 | 〜300ms |
| 7 | `session.point(...)` — Gateway へリクエスト送信 | 〜330ms |
| 8 | SSE で本文が流れ始める | 〜3500ms |
| 9 | 最終オブジェクト受領 → `markWhatTheAnswerIsAbout` → 回答の枠 | 〜5500ms |

### 3.2 配置の規則（現状）

置き場所は `BubbleAnchor` が決める（`BombSquad/Views/VisionBubblePlacement.swift`）。

```swift
struct BubbleAnchor: Equatable {
    var frame: CGRect?        // 対象の枠。これだけが「対象がどこか」を知っている
    var userTopLeft: CGPoint? // ユーザーがドラッグした位置。frame より優先
}
```

**クリック点を保持するケースは意図的に存在しない**（後述の経緯による）。

書き換えてよいのは3つだけ:

- `setMark` — AXが実測した枠が取れた時（新しい主題）
- `showAnswerFrame` — 回答が対象を指した時
- `noteBubbleMoved` — ユーザーがドラッグした時

さらに直近で追加した規則が2つ:

- **伸び縮みでは配置を解き直さない**（`VisionBubblePlacement.resized`）。左上を保って下へ伸びる
- **本文が1文字でも出た後は動かさない**（`showAnswerFrame(movesBubble:)`）

## 4. 実測データ

### 4.1 AXが実測できた場合（正常系）

```
vision.point candidates=88 hit=true
```

枠はクリック後 **約300ms** で確定する。リクエスト送信（330ms）より**前**。
この場合、要求される順序（位置 → 文章）は満たされている。

### 4.2 AXが何も実測できなかった場合（問題が出る系）

```
09:54:06.485  vision.point   candidates=0 hit=false
09:54:10.029  vision.firstContent sinceAsk=3544ms       ← 本文が流れ始める
09:54:11.534  vision.result  mode=answer highlight=resolved ← ここで初めて枠が決まる
```

- AX候補が **0件**。クリック時点で対象の場所は**分かっていない**
- 候補0件で使える唯一の枠はモデルが返す `annotations[0].box`。
  `targetCandidateId`は候補リストのidなので矩形へ変換できない
- それは**ターン最終の検証済みオブジェクトからしか読んでいない**（後述）
- 結果: 本文が3.5秒で出始め、枠は5.5秒。**約1.9秒、文章が出た後に位置が決まる**

**この1.9秒がユーザーの見ている「解説が1〜2行進んでからバブルが移動する」**。

### 4.3 なぜAX候補が0件になるのか（未調査）

同一セッション内でも `candidates=88` の時と `candidates=0` の時がある。
アプリ・画面種別との相関は未特定。**ここは調査が必要**。
AX候補は操作系13ロールに限るが、候補数はクリック地点ではなく画面全体の件数である。本文・画像・
グラフ・canvasを指して**ヒットしない**ことは正常でも、ボタン等がある画面の候補0件は収集側の問題を
疑う。`vision.point`を`collectorEmpty / pointMiss / measured`へ分類し、visited node、収集起点、pass、
WebArea、打切り理由を併記して切り分ける。

## 5. 経緯（レビューで最も重要な情報）

**同じ「バブルがリングの位置に飛ぶ」不具合を4回直して4回とも再発した。**
各回の修正は、それぞれ別の機構を1つずつ塞いだだけだった。

| 回 | 修正内容 | 破れ方 |
|---|---|---|
| 1 | `showRing` から配置呼び出しを削除 | アンカーへの代入が残っており、0.1秒ごとのreflowが実行した |
| 2 | `showRing` からアンカー代入も削除 | `setMark` がクリック点をアンカーにしていた |
| 3 | `setMark` で実測frameを優先 | AXが測れない時はクリック点のままだった |
| 4 | `BubbleAnchor` から点のケースを型ごと削除。reflowは解き直さない | （今回の報告） |

### 分かった構造的な原因

**置き場所は3つの入力から解かれる関数だった。**

```
位置 = f(アンカー, カードのサイズ, 避ける矩形)
```

不変条件は毎回**アンカーについてだけ**書かれていた。ところがクリックは残り2つを自分で変える:

- `beginPointing()` が回答を「ここを読んでいます…」に差し替える → **高さが変わる**
- `showRing` が実測frameを `avoid` から外す → **避ける矩形が変わる**

そして 0.1秒ごとのタイマーが `placeBubble()` を呼び直す。
**アンカーを守っても、他の2つが変われば別の場所に置かれる。**

加えて「クリック点を使わない」は**型ではなく約束**だったので、次の編集で必ず破れた。

## 6. 未解決の核心

**AXが実測できない画面で、「文章より先に位置を確定する」をどう成立させるか。**

現状の建て付けでは成立しない。理由:

1. AX候補が0件なら、クライアントは対象の場所を知らない
2. 唯一の枠はモデルの応答にある
3. その値を**ストリーム途中から読まない**という規則がある

3の理由は `api-gateway/lib/server/vision-engine.ts:170` に書かれている:

> The final event still carries the fully parsed and validated result. Deltas are for
> reading, never for deciding: the mode, the candidate ID, and the uncertainties come
> only from the complete object.

一次モデルが応答途中で落ちた場合、表示を `reset` で撤回して二次モデルへ切り替えるため、
未検証の部分値で状態を決めると撤回できない、という設計。

### 初版の見落とし（訂正済み）

Gateway のレスポンススキーマのプロパティ順:

```ts
required: ["mode", "message", "observations", "uncertainties", "targetCandidateId"]
```

**`targetCandidateId` が最後**にある。structured output は概ねスキーマ順に生成されるため、
対象IDは**本文・観察・不確実性を全部書き終えた後**に出てくる。

`message` が2番目にあるのは「最初の一文字を早く出すため」の意図的な設計（同ファイル167行）。
初版は「`targetCandidateId`を`message`より前に置けば位置を先に得られる」と結論したが、これは誤り。
`targetCandidateId`は送信済みcandidateのidであり、問題系の`candidates=0`では矩形へ変換できない。
実際に`highlight=resolved`となる経路は`annotations[0].box`である。

Gatewayから早期配置を得る将来案は、idではなく矩形`subjectPlacement`を専用SSEイベントとして送るもの。
公開中クライアントへの影響を避けるため、新クライアントが明示要求した時だけスキーマとpromptを変える。
部分値、一次モデル失敗時のreset、fallback時の再配置まで契約を決めてから採否を判断する。

## 7. 設計の選択肢

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A** | 現状維持（AXが測れない時はバブルを動かさない） | 実装済み。読書中に動かない | 枠とバブルが離れる。対象の隣という設計思想を一部放棄 |
| **B** | AXが測れない時はリングの隣へ | 常に対象の近く | **オーナーが明確に却下** |
| **C（初版は誤り）** | `subjectPlacement`矩形をopt-inで本文より先に流す | バッファ時間を短縮できる可能性 | Gateway契約変更。reset/fallback規則が必要。実測後の最適化 |
| **D** | バブルは1ターン中一切動かさない（開始時に決めた位置に固定） | 最も単純。絶対に動かない | 対象の隣に置くという製品の中心的な主張を捨てる |
| **E** | AX候補0件の原因を潰し、実測率を上げる | 根本的。正常系が広がる | 原因未特定。AXが本質的に返さない画面は残る |
| **F（採用）** | 1ターン1配置の状態機械。未解決時だけ最終枠まで本文をバッファ | クライアントだけで「位置→文章」を保証。resetは未表示draftを捨てるだけ | 問題系の初文字が実測3.5秒→5.5秒 |

**Fを先に採用し、Eのための計測を同時に入れる。** `AXUIElementCopyElementAtPosition`は短命probeを
通してから。Cは運用データでバッファ時間が問題だと確認できた場合だけ検討する。

## 8. レビュアーに聞きたいこと

1. **そもそも「バブルが対象の隣に移動する」という設計は正しいか。**
   移動を伴う限り、どこかに「動く瞬間」が生まれる。
   固定位置（右下）＋枠だけが動く、の方が体験として安定しないか。

2. **案C（対象IDを先に流す）の危険性をどう評価するか。**
   「未検証の値で状態を決めない」という規則を、配置に限って緩めてよいか。
   配置は撤回可能（動かし直せる）なので、mode や uncertainties とは性質が違うと考えているが。

3. **AX候補0件の切り分け方。**
   どのアプリ・どの画面種別で0件になるかを効率的に特定する方法。
   現状の記録は `candidates` の件数だけで、アプリ名は**意図的に記録していない**
   （動作記録にウィンドウタイトル・アプリ名・ホスト名を載せない規約があるため）。

4. **0.1秒ポーリングのreflowは妥当か。**
   SwiftUI の `NSHostingView` は内容の高さ変化を窓に通知しないため、
   タイマーで `intrinsicContentSize` を監視して窓をリサイズしている。
   より正しい方法（レイアウト通知、`NSViewRepresentable` の再設計など）があるか。

5. **4回再発した件について、他に構造的な手当てが要るか。**
   型からケースを消す（クリック点を表現不能にする）以外に、
   この種の「規則が約束でしかない」状態を潰す方法。

---

## 9. 壊してはいけない不変条件

レビューで代替案を出す際、以下は製品の他の部分が依存している。

- **印は常に1つだけ。** リング → AXの枠 → 回答の枠、と入れ替わる。同時に2つ描かない
- **バブルは枠を覆わない。** 枠の情報がバブルに隠れると、印の意味が消える
- **座標変換は `VisionPointerResolver` の2関数だけ。** 3つ目の式を書くと二次ディスプレイでずれる
- **動作記録に本文・アプリ名・ウィンドウタイトル・ホスト名を載せない。** 型として書けないようにしてある
- **`api-gateway` の `main` への push は本番デプロイ。** プロンプト/スキーマを触ると公開中のクライアントの挙動も変わる
- **ユーザーがドラッグした位置は、次に指すまで勝つ**
