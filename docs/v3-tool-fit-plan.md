# v3 ツール適合計画（Skills とユーザーファクト）

最終更新: 2026-07-30 ／ ステータス: 現行（ブランチ `v3`）

マイルストーンの一覧と進捗はマスタープラン R8 が正、API契約は `api-gateway/docs/api-contract.md` が正、
実装の正は現行コード。本書はその R8 の設計根拠と決定事項を持つ。

## 1. なぜやるか

汎用の理解だけでは、ユーザーが実際に使っているツールの作法まではカバーできない。
ツール個別の適合を積み上げることが、そのままエンタープライズ導入の入口になる。

- ツール（Slack / Gmail / Salesforce / freee / SmartHR / GA4 …）を1つずつ理解する
- 業種パッケージ（金融SaaS、HR、デザイン等）としてまとめて開放する
- 個社の業務フローに特化した定義を納める＝FDEモデルの商材

したがって v3 の成否は「機能が動くか」ではなく、**ツールを1つ増やすコストが定数に
収まっているか**で判定する。定数に収まっていなければ、上の3段は積み上がらない。

## 2. 名前と階層

精度レイヤーの正式名称は **Skills**。「レシピ」「アタッチメント」「アプリパッケージ」は
すべて廃語とする。

| 層 | 内容 | 誰が更新するか |
|---|---|---|
| ベース | 話者、宛先、所有者、安全性、基本判断 | 製品（中立を保つ） |
| ツール | 個別製品のUIの意味と作法 | 製品 |
| 業務 | 業種・職種のドメイン知識 | 製品／パートナー |
| 個社 | その会社固有の運用 | FDE |
| セッション | いま見えている画面 | 実行時（永続しない） |

原則:

- **Skills はデータであり、制御フローに触れない。** Skill が1つも当たらなくても汎用経路は無傷。
- **サイレント注入を禁止する。** 有効な Skill は常にUIから見える。
- **基礎プロンプトは中立のまま。** 特定製品・ドメインの語彙はSkill側にだけ置く。
- 提供元単位ではなく製品単位で分ける（Google ではなく Gmail / Docs / Sheets）。

## 3. Skill の構造

```ts
type Skill = {
  id: "slack";
  layer: "tool" | "domain" | "tenant";
  detect: (signals: AppSignals) => boolean;
  reading:     string;  // 画面の読み方
  conventions: string;  // そのツールでの自然な書き方
  affordances: string;  // そのツールでできること（提案に使える機能）
  attention:   string;  // 見るべき状態（未読・自分宛・期限）
  facts: readonly FactKey[];  // このツールで知る価値のある事実
};
```

`facts` を Skill 自身に持たせるのが要である。Skills とファクト記憶を別々に管理すると、
ツールを増やすたびに両方へ手を入れることになる。Salesforce の Skill を1ファイル足せば、
読み方・作法・機能・注意点と「そこで何を覚えるべきか」が同時に定義される。

### セクションと用途の対応

Skillの利用者は2種類あり、必要なセクションが違う。全部を全員に渡すと、トークンを使って
それぞれを少しずつ悪くする。

| 用途 | 渡すセクション | 向いているツール |
|---|---|---|
| 先回り文案（suggest） | reading / conventions | Slack、Gmail — 会話が主 |
| Vision・Copilot | reading / affordances / attention | GA4、Adobe — 操作が主 |

会話系のSkillはconventionsが厚くaffordancesが薄い。操作系はその逆になる。
どのセクションを持つかはSkill側の任意で、無いセクションは単に注入されない。

### 検出について

大半のB2B SaaSはブラウザ内で動くため、bundle ID はどれもブラウザのものになる。
**一次シグナルはページのホスト名**とし、Accessibility から取得する（Safariはウィンドウの
`AXDocument`、Chromium系は`AXWebArea`の`AXURL`）。パスとクエリは取得しない — 製品の判定に
必要なのはホストだけで、残りはユーザーの中身だからである。

ウィンドウタイトル判定を一次にしてはいけない。M1のGmailがこれで外れた: Workspace の Gmail は
タブタイトルが「件名 - アドレス - 組織名 Mail」で、**製品名をどこにも含まない**。タイトル一致は
個人の @gmail.com アカウントだけを拾い、つまり顧客以外の全員を拾う。ホストなら
`mail.google.com` で一意に決まる。

この一手で SaaS カテゴリ全体が同じ形で載る: GA4 は `analytics.google.com`、Salesforce は
`*.lightning.force.com`、freee は `*.freee.co.jp`、SmartHR は `*.smarthr.jp`。

Vision の初回観察は既に毎回ツール名を特定できているので、ホストが取れない場合の
モデル判定を二次経路として後から足す。

### 数百・数千ツールへの拡張（将来課題）

PowerPoint、Blender、Word、Excel、VS Codeのようなネイティブアプリから、Meta広告、
TikTok広告のように1製品内に多数の管理画面を持つSaaSまで対象にすると、現在の
「1製品1ファイルをregistryへ手動登録し、先に一致した定義を採用する」方式は運用上の上限に達する。
M6で追加コストが定数に収まることを確認した後、マスタープランR8のM7として次へ移行する。

#### カタログの単位

製品数と画面数を同じものとして数えない。**Skillは製品単位**を維持し、その中を画面・作業単位の
moduleへ分ける。たとえばMeta広告ならcampaigns / ad sets / ads / audiences / billing、
PowerPointならediting / slideshow / exportを持つ。共通知識を製品Skillに、画面固有の読み方・
機能・注意点をmoduleに置き、実行時には該当しそうな1〜3 moduleだけを添付する。

管理対象は次の3つへ分離する。

1. **製品カタログ** — 正式名、表示名、host、bundle ID、app name、所有者、状態、version
2. **画面module** — 製品内のsurface判定と、その画面だけのreading / affordances / attention
3. **Skill本文** — 製品共通のreading / conventions / factsと、業務・個社レイヤー

検出条件は任意のTypeScript関数ではなく、原則として次の宣言的データにする。

```ts
identifiers: {
  hosts: ["analytics.google.com"];
  bundleIds: ["com.microsoft.Powerpoint"];
  appNames: ["Microsoft PowerPoint"];
}
```

ビルド時にhost→製品、bundle ID→製品の索引を生成する。Gatewayを製品名の正本とし、macOS側は
応答された表示名を描画するだけにする。クライアントへSlack / Gmail等の製品名判定を重複実装しない。

#### 検出とfallback

検出は安価で確実な順に行う。

1. host、bundle ID、正式なapp nameで製品を確定する
2. 製品確定後、スクリーンショットとAXから製品内moduleを絞る
3. 確信できなければ製品共通Skill、製品も不明なら汎用経路へ退化する

誤ったSkillを強制適用するより、Skill無しで汎用理解を使う方を選ぶ。全Skillをモデルへ渡して
選ばせる方式は禁止する。カタログが増えても、1リクエストのプロンプト量と判定時間をほぼ一定に保つ。

#### 追加・改善の運用

ツール追加は次の同じ工程を通す。

1. 利用頻度、事業価値、誤操作時のリスクから優先順位を決める
2. テンプレートから製品定義と最初のmoduleを作る
3. 通常例・境界例・誤検出例・危険操作を含むgolden caseを10〜20件用意する
4. 自動評価で検出、初回ターン適用、回答品質、汎用fallbackの非劣化を確認する
5. beta / canary / stableの順で段階公開し、version単位で即時に戻せるようにする
6. 実利用で不足した画面だけmoduleとして追加し、製品全体を複製しない

未対応ツールの発見にテレメトリを使う場合は明示的な同意を前提とし、未一致のhost／bundle IDの
集計に限定する。スクリーンショット、画面本文、パス、クエリは収集しない。

規模ごとの移行目安:

- 〜50製品: 現行の1製品1ファイルで知識と評価方法を固める
- 50〜500製品: 宣言的定義、生成registry、識別子の競合テストへ移行する
- 500製品〜: カタログを独立管理し、該当Skill／moduleだけを遅延ロードする
- 数千製品: owner、version、審査、段階公開、利用状況、rollbackを管理画面で運用する

M7の完了条件:

- 製品追加でmacOSクライアントを更新しない
- host、bundle ID、IDの重複と曖昧な一致をビルド時に検出する
- 1回に注入するmoduleは原則1〜3個、プロンプト量はカタログ総数に比例しない
- 初回ターンの正しいSkill適用率と、誤Skill適用率をgolden caseで継続計測する
- Skill無しの画面で汎用品質が落ちない
- 公開済みSkillをversion単位で停止・rollbackできる

## 4. ユーザーファクト

### 破綻させない仕組み

確信度・観測回数・減衰を持つ設計を検討したが、**採用しない**。あれが必要になるのは
自由文のメモを追記し続ける前提のときで、キーを閉じて upsert にすれば総量は仕様上有限になる。

```
scope: global   → display_name / primary_language / org_name / role
scope: slack    → account_name / handle / workspace
scope: gmail    → address / signature_name / org_domain
```

「Slackでの表示名」は何回検出しても永久に1行。アプリ5個でも合計30行前後、値は各120字上限。
**プロンプトへ注入するのは `global` と現在のツールの scope だけ**なので、常時10行・400字程度で
固定される。使い続けても重くならない。

キー語彙に無いものは保存しない。これが唯一のガードレールで、これだけで足りる。
破綻回避の担保は減衰ではなく、**ユーザーがいつでも一覧・編集・削除できること**に置く。

### 保存先

```
bs_user_facts (user_id, scope, key, value, updated_at)
  unique (user_id, scope, key)
```

全件でも数十行なので、差分同期・cursor・tombstone は持たない。全件 pull/push の
last-write-wins で足りる。旧メモリの複雑な同期機構は引き継がない。

質問の抑制状態だけは別テーブルへ置く。

```
bs_fact_prompts (user_id, scope, key, ask_count, declined_at, updated_at)
  unique (user_id, scope, key)
```

値と抑制状態を1行に混ぜない。**保存済みであること自体が「もう聞かない」理由**なので重複はせず、
ユーザーが値を消せば同じキーをまた聞ける（回数は引き継ぐ）。キーは同じ閉じた語彙なので、
この表も構造上有限である。

### 聞き方

検出専用の呼び出しは作らない。suggest は Compose を開くたびに画面を読んで構造化JSONを
返しているので、そのスキーマへ `fact_candidate` を1つ足すだけでよい。追加のレイテンシも
コストもゼロ。

```
Slackでの表示名は「Kaya Matsumoto」ですか？   [はい]  [いいえ]
```

守れないなら機能ごと入れないほうがよい規則:

- 1セッションにつき最大1問
- 既知キー・拒否済みキーは二度と聞かない
- 未回答のまま閉じたら保留、同一キーは通算3回で打ち切り
- 確信が高い候補だけ。曖昧なら聞かない
- 画面文字列を確認文へ出すため、値の長さ・改行・制御文字を制限し、必ず引用符で囲んで
  「画面から読み取った値」として提示する（プロンプトインジェクション対策）

「いいえ」の意味は「保存しない」に統一する。「値が違う」と分けるとUIが2倍になり、
訂正は管理画面でできる。

### もう1つの取得経路：セットアップウィザード（未実装・案）

画面からの検出は「1セッション1問」で、性質上ゆっくりしか埋まらない。手間をかけてでも早く精度を
上げたいユーザーのために、**「あなた自身について聞かせてください」という対話形式で、精度に効く項目を
決め打ちで埋める**経路を用意する価値がある。かけた手間がそのまま精度に返る、という交換が成立する。

置き場所の条件:

- **初回起動には置かない。** 権限設定を終えた直後に質問を並べるのは、いちばん離脱する場所である。
- マイページ（管理画面）に常設し、加えて**ある程度使った段階**で導線を出す。何に効くのかを
  実感した後の方が、答える動機がある。
- **完全にオプショナル。** 1問も答えなくても全機能がそのまま動く。これはSkillsと同じ性質で、
  「無ければ無いで成立する加算レイヤー」であることを崩さない。

書き込み先・語彙・上限は画面検出と完全に同じ（`bs_user_facts`、閉じたキー語彙、upsert）。
経路が増えるだけで、記憶の総量も管理画面での見え方も変わらない。ウィザードで答えた項目は
埋まったことで自動的に再質問の対象から外れる。

## 5. 全層に共通する前提

プロンプトには「なぜ呼ばれたか」を必ず定義する。ホットキーで呼び出された時点で
ユーザーはサポートを求めており、入力欄の手前にあるものはユーザーへ向けられた依頼や
質問である可能性が高い。画面上の証拠が明確に否定しない限りユーザーを返す側とみなす。

- 会話の大半が画面外でも、文脈不足を理由に生成を控えない
- 助けが必要な場面で何も出さないことを最悪の結果として扱う。空振りより過剰支援を選ぶ
- 依頼の実行者がユーザーなら、文案はユーザーが何をするかを述べる。同じ依頼を相手への
  指示として返さない

この前提は先回り文案だけでなく **各 Skill を書くときにも共有する**。M0.5 で共通コアへ実装済み。

## 6. 判定基準

M5 到達後に測る:

1. 聞かれた回数と「はい」率 — 低ければ検出の質、高頻度なら鬱陶しさ側の失敗
2. ユーザーが後から編集・削除したファクトの割合 — 誤検出率の代理指標
3. ファクト総行数の推移 — 設計どおりなら数週間で頭打ちになる。増え続けるならキー語彙が漏れている
4. ファクト注入前後で、文案をそのまま送った率

各マイルストーン共通の受け入れ条件: **Skill が当たらない画面で汎用品質が落ちていないこと。**

## 7. 却下した案

- **確信度・観測回数・有効期限を持つ圧縮メモリ** — §4のとおり、キーを閉じれば不要。
  未検証の学習ループの上に減衰エンジンを積むのは順序が逆。
- **Slack のメンション自動付与** — 投入はクリップボード＋⌘Vのペーストであり、表示名に
  スペースを含む文字列は Slack のメンションとして解決しない。通知の飛ばない偽メンションは
  無いより悪い。呼びかけ（「〇〇さん、」）で代替する。
- **文体・関係性メモリの継続** — M0 で全層から削除済み。
