## 1. 何を作るのか（機能の定義）

**画面を理解して、人間に次の行動を案内する視覚コパイロット。** 自律操作エージェントではない。
最終操作は常に人間が行う。Universal I//O の中の1機能であり、送信レビュー・受信変換と
同じ「中間レイヤー」思想の視覚版。

成功の姿（ユーザー体験としての北極星、v3計画から引き継ぎ）:
> 「開始」を押したら、あとは画面の光る場所を順番に押していくだけで、目的の答えにたどり着く。
> 最後のステップでは案内ではなく目的の答えを読み上げて完了する。

## 2. 過去2回の挑戦の総括（事実と死因）

### 第1次: プロトタイプ〜v3（自由文マーカー方式、2026-07-05〜07-13）

- **構成**: 強いマルチモーダルモデル1コール＋自由文回答＋`[[target:ラベル]]`マーカー。
  位置解決はOCR/AXのラベル文字列一致。初期はDOMも参照していた。
- **良かった点**: 着想から約15分で動き、体感8割の品質。画面理解そのものは最初から成立していた。
- **死因（実測・記録済み）**:
  1. **同名ラベルの取り違え** — 「概要」が2つある画面でラベル一致は構造的に区別不能。
  2. **再現性のなさ** — マーカーが出たり出なかったり（プロンプト注入の履歴汚染、
     モデルの保守化ドリフト。7/6 の記録）。
  3. **入力の劣化蓄積** — 画像縮小(長辺1,600px)・出力上限(1,200tok)・履歴削除・
     高速初手モデル(qwen)の混入が段階的に積まれ、後期のv3は初期の15分版より
     貧しい入力で動く別物になっていた。
  4. **DOMの喪失** — 「拡張に依存しない」という製品戦略判断でDOMを外し、ブラウザUIで
     最強のセンサーを失った。その穴を後段の複雑な判定で埋めようとした。

### 第2次: v4（4役職分割＋決定論ゲート、2026-07-14〜15）

- **構成**: Observation / 版付きPack / Gateway発行Run（署名・revision）/ Planner /
  Grounder / Verifier / Renderer の役割分離。fail-closedゲート。v3と並走（shadow）。
- **良かった点**: trace/usage/eval の計測基盤。候補収集（AX/OCR、親文脈付き）。
  画面安定検知。レシピ無しの汎用モデル判定が実画面で verified を返せることの実証。
- **死因（実測・記録済み）**:
  1. **配線が壊れていても気づけない** — snapshot競合でv4が一度も動かないまま
     「production readiness」を宣言。ローカルテスト合格をe2e完成と誤認。
  2. **独立でない検証は検証にならない** — 各役職が同じ痩せた入力を見ており、
     多段化は堅牢性でなく同じ誤りの増幅だった。
  3. **正解の決定権の分散** — モデルが正しく理解しても、ラベル一致が別要素を選び、
     ゲートが正しい進捗を拒否した（grounder disagreement → 正答のハイライト抑止を
     ログで確認）。
  4. **フォールバックが失敗を隠す** — 旧経路・別モデルへのサイレント切替で、
     ユーザーが試しているのが新旧どちらかすら不明になった。
  5. **検証順序の逆転** — 最高品質モデルで上限を測る前に、制御構造と速度最適化を
     先に作った。オーナーは一貫して「まず最高品質」と要求していたが、
     実装の受け入れ条件にならなかった。

### 2回に共通するプロセスの死因

- 「動き続けること」を暗黙の制約にした結果、並走・フォールバック・フラグが増殖し、
  二重実装が恒久化した（ビッグバン失敗の反動での過剰防衛）。
- 完了の定義が「コードが書けた」であり、「実画面でその経路が動いた証拠」ではなかった。

## 3. 動かせない制約（すべての案が従う前提）

1. **観測の限界**: 見た目が同一で内部状態が異なる画面は、構造情報なしには原理的に判別
   不能。100%はどのアーキテクチャでも約束できない。目標は「観測可能なものを高精度に、
   確証がなければ誤案内せず明示的に止まる」。
2. **製品戦略**: 標準体験はゼロインテグレーション（インストールして権限を許可すれば
   どのアプリでも動く）。拡張・API連携は精度アドオン（個社/上位プラン）として許容。
3. **軽快さと堅牢さが最大プライオリティ**（全体方針）。ただし堅牢さの置き場所は
   決定論的外殻であり、LLMの多段呼び出しではない（第2次の教訓）。
4. **人間が最終操作**。誤ハイライトは人間のミスを誘発するため、エージェント制御と
   同水準の証拠管理が必要。

## 4. 設計空間の全列挙

結論に飛びつかないため、各軸の選択肢を利点・欠点・証拠付きで列挙する。
**太字**は§5のCTO判断で採る案。

### 軸A: 認知構造（誰が考えるか）

| 案 | 内容 | 利点 | 欠点・証拠 |
|---|---|---|---|
| A1 | **単一コール**（理解・案内・対象選択を1回で） | 情報損失なし・接合部なし・最速 | モデル品質に全依存。上限未測定（これを測るのが第3次） |
| A2 | 2段（案内→操作後に進捗判断） | 進捗判断が新しい画面という独立証拠を得る | 「別人格Verifier」ではなく「次ターンの判断」として実装すれば実質A1の反復 |
| A3 | 4役職分割（第2次） | 各段が計測可能・理論上は誤り抑制 | **実測で死亡**。独立でない検証は増幅装置。接合部が壊れる |
| A4 | エージェンティックループ（computer-use型、モデルがツールを自律呼び出し） | 業界の実証多数 | 自律操作向き。人間案内では往復が過剰、体験が重い。将来の自動操作モードでは有力 |

### 軸B: センサー（何を見せるか）

| 案 | 内容 | 利点 | 欠点・証拠 |
|---|---|---|---|
| B1 | 画像のみ | 依存ゼロ | 座標が出せない・文字精度に限界 |
| B2 | **画像＋OCR** | 文字の正確な位置 | 構造（親子・状態）が無い |
| B3 | **画像＋AX** | 親子関係・selected/expanded・矩形。macOSネイティブに強い | ChromeはAXEnhancedUserInterface依存で品質変動。Electronアプリはまちまち |
| B4 | **画像＋DOM由来情報** | ブラウザUIで最強の構造 | 取得経路が論点: Chrome AX WebArea（拡張不要・DOM由来）で標準経路、拡張は精度アドオン。第1次で外したのは戦略判断であって精度判断ではない |
| B5 | アプリ固有API（GA4 API等） | 最高精度 | 個別連携=ゼロインテグレーション違反。個社ハーネスの領域 |
| B6 | ユーザー協働（見つからない時に人間に探させる/教えさせる） | 原理的限界の脱出口 | UX設計が必要。「確証がなければ止まる」の先の一手として有望、挑戦4以降の候補 |

→ Spot Visionは同一captureの画像とAXを固定する。初期コメントは画像中心、後続質問は同じ画像＋
固定AX候補＋履歴を1コールへ渡す。DOM/OCRはAX候補欠落の実測後に一つずつ加える。

### 軸C: 位置決め（どこを光らせるか）

| 案 | 内容 | 利点 | 欠点・証拠 |
|---|---|---|---|
| C1 | モデルの自由座標（bbox） | 依存なし | 不正確が実証済み（VLM座標は信頼できない） |
| C2 | ラベル文字列一致（第1次） | 単純 | **同名ラベルで死亡（実測）** |
| C3 | **candidate ID選択**（列挙した候補からモデルがIDで選ぶ） | 座標はコードが保証・同名は親文脈で区別・幻覚した場所を指せない | 候補収集の網羅性に依存。Canvas等で候補ゼロ |
| C4 | Set-of-Marks（画像に番号を焼き込んでモデルに番号で答えさせる） | 研究で実績。候補とビジュアルの対応が確実 | 画像加工の実装。C3で不足した場合の強化オプション（挑戦4候補） |
| C5 | 位置なし案内（「左メニューの下から2番目」と言葉だけ） | 実装ゼロ | 製品価値の核（光る場所を押すだけ）を放棄 |
| C6 | 低信頼bbox経路（候補ゼロのCanvas等のみC1を明示的に使う） | 空白を埋める | 必ず低信頼と表示・記録して使う |

### 軸D: 状態と計画（何を覚えるか）

| 案 | 内容 | 利点 | 欠点・証拠 |
|---|---|---|---|
| D1 | 全手順を最初に固定（第2次のRun/レシピ） | 監査可能・進捗が明確 | UI変更・想定外画面で脆い。plan照合の配線が壊れて死亡 |

| D3 | ステートレス（毎回ゼロから） | 最単純 | 目的を見失う。マルチターンの案内が成立しない |
| D4 | サーバ保持の署名付きRun（第2次） | 改ざん耐性・課金/監査 | 検証段階には過剰。**計測資産としてのみ維持**、体験に関与させない |

| 案 | 内容 | 利点 | 欠点・証拠 |

## 5. CTO判断（第3次挑戦の構成）

**選択（2026-07-16更新）: 固定snapshot単一経路 × C3 × D2 × E2 × G1 × H2+H3**

```
Spot Vision（1枚の固定capture）
  ├─ 画像 → Luna VLM → 短い初期コメント
  └─ AX収集を並列実行し、同一captureへ固定
       ↓
後続質問: 同じ画像 + 固定AX候補 + 履歴 → Luna VLM 1コール
  出力: answer|guide|clarification + optional candidate ID
       ↓ candidate IDがある場合のみ
決定論的な矩形変換 → スクリーンショット拡大・赤枠

Copilot（後続段階）
  人間のクリック → 画面安定化 → 新しい固定snapshot → 同じ1ターンを反復
```

**この構成を選ぶ理由（他を選ばない理由）**:
- 第1次の死因（同名ラベル・再現性）はC3とE2が直接潰す。第2次の死因（接合部・検閲・
  入力劣化）はA1とH1廃止が直接潰す。過去の死因に同じ形で当たらない最小構成がこれ。
- ユーザーに内部経路の選択を要求しない。回答と案内を同じ出力契約にし、candidate IDの有無だけで
  決定論的レンダラーを動かす。
- Spot Visionでは画像・AXを途中更新せず、画像だけ古くAXだけ新しい不整合を作らない。
- DOM/OCRは、AX候補欠落の実測後に追加する精度レイヤーとする。
- 堅牢性は決定論的外殻（H3＋trace/replay＋実効モデル記録）で第2次より**強く**なる。

**ただし、これはアイデアであり、実測で棄却されうる。** 確定仕様ではない。

### 検証モードの受け入れ条件（fail-loud）

1. 各比較区間で固定した実効モデル・reasoning effortを開発UIとtraceで確認する。
   使えなければ明示的エラー。フォールバック発生 = テスト失敗。最初の品質上限確認は
   GPT-5.6 Sol / `max`、成立後の最初の軽量化比較はGPT-5.6 Luna / `none`とする。
2. 位置指定は candidate ID のみ（低信頼bbox経路は件数を記録し、UIで低信頼と明示）。
3. 同名ラベル（GA4「概要」×2）を親文脈で正しく区別できる。
4. stale capture / capture scope不一致の採用 0。
5. 実効モデル・経路・fallback有無を毎ターン記録し、開発ビルドで表示。
6. 全ターンが trace から再生可能。
7. 成立確認後に初めて速度・コスト最適化（画像縮小・履歴圧縮・軽量モデル・キャッシュ）に
   着手する。順序の逆転は前回最大の誤り。

## 6. 反復ロードマップ（失敗前提）

### 挑戦の運用ルール

- **1挑戦 = 仮説 + 実装 + 実画面計測 + 判定 + 剖検**。挑戦の開始時に仮説と棄却条件を
  本書に書き、終了時に剖検（何が死んだか）を追記する。
- 挑戦の切り替え時は git tag を打つ（例: `challenge-3-start` / `challenge-3-end`）。
- 並走は比較計測の期間のみ（時限）。挑戦N+1 が立った時点で挑戦N の経路は削除する。
- 完了の定義は常に「実画面でその経路が動いた証拠（trace/usage）」。コード完了・
  テスト合格は完了ではない。

### 挑戦3（本書の構成）

開始記録（2026-07-16）:

- 復帰点: tag `challenge-3-start`（main `93f35f7`）。
- 開発branch: `experiment/copilot-challenge-3`。runtime feature flagで新旧を切り替えない。
- 隔離境界: 新Gateway endpoint `/api/ai/screen-understanding` と新しいmacOS Session/Viewを
  白紙実装する。既存`VisionSession`、`GatewayNavigateClient`、`/api/ai/navigate`、v3/v4 engineを
  importしない。共有するのはPanelController、capture、画像表示、入力UI、認証、Gateway transport。
- 最初のMVPは**Vision-first**: immutableな1枚のcaptureについて、短い初期理解を返し、
  追加質問へ答えるところまで。candidate選択、ハイライト、クリック後進捗判定は、このMVPの
  実画面成立を確認するまで接続しない。
- 完了済み: fail-loudなGPT-5.6 Sol Responses API engine/endpointを独立実装。固定条件は
  `gpt-5.6-sol` / `detail: original` / `reasoning.effort: max` / 25,000 output tokens / fallbackなし。
- 完了済み: macOSに`Challenge3VisionSession` / `Challenge3VisionSessionView` /
  `GatewayScreenUnderstandingClient`を独立実装。`SessionCoordinator`のcapture完了後という1箇所だけを
  新Sessionへ切り替え、旧`VisionSession`、Navigator、Copilotへの実行入口を外した。パネル・capture・
  画像表示・入力UI・認証transportは共有している。
- 検証済み（コード）: web test 68件、対象lint、TypeScript、Next production build、macOS Debug
  `CODE_SIGNING_ALLOWED=NO`が成功。
- 初回実画面スモーク（2026-07-16）: GA4の「ユーザーの環境の概要」をcaptureし、実効モデル
  `gpt-5.6-sol`で画面、プロパティ名、表示中の指標を正しく要約した。続く「どのソーシャルメディア
  からアクセスがあるか」という質問には、現在の画面だけでは判定できないと明示し、確認先を案内した。
  UI表示は16,791 ms、Gatewayでは3回の`POST /api/ai/screen-understanding`がすべて200で、
  17.0秒、18.0秒、17.3秒だった。モデル名と経路が開発表示され、fallbackや旧navigate経路への流入は
  観測されなかった。これを**Vision-firstの初期理解＋追加質問の成立**と判定する。
- 未検証: candidate収集・選択、ハイライト、クリック後の新規captureによる進捗判定。今回の成功は
  挑戦3全体やGA4 golden pathの合格を意味しない。
- 方針更新（2026-07-16）: オーナーがVision-firstパネルの初回成立を確認し、次段階への移行を承認。
  Sol / `max`は品質上限の基準として保持し、実行設定をGPT-5.6 Luna / `none`へ固定変更する。
  fallbackなし、`detail: original`、25,000 output token上限、実効設定の開発表示は維持する。

## 7. 前身文書から引き継ぐ資産（吸収済み）

### 7.1 正のユーザー体験: ナビゲーションモード（2026-07-07 オーナー仕様。エンジンが変わっても不変）

実装・レビューはこの体験に照らして判断する。

> **「開始」を押したら、あとは画面の光る場所を順番に押していくだけで、目的の答えにたどり着く。**

1. 質問すると、回答と一緒に「ナビゲーション開始（Nステップ）」ボタンが提案される。
2. 開始を押すと、パネルは**画面右下の小さな帯**に変形する。帯には「ステップ・目的・現在の
   指示・終了ボタン」だけ。中央の大パネルは出さない。
3. 現在のステップの対象が**実画面上で赤くハイライトされ、消えない**（次のステップまで出続ける）。
4. ユーザーがハイライトされた場所を**自分でクリック**する。ナビゲーション中は
   「◯◯を押す」承認ボタンは出さない（2系統の操作が並ぶと誰も理解できない）。
5. **パネルの外をクリックしてもナビゲーションは終わらない**。クリックを検知したら自動で
   画面を撮り直して進捗を確認する（手動の「撮り直す」も保険として残す）。
6. 最後のステップでは案内ではなく**目的の答えを読み上げて**完了する。
7. 帯の「終了」またはショートカット（右Shift2回）でいつでも離脱できる。

（背景: 従来パネルは「外に触れたら閉じるモーダル」= `handleResignActive` → `closePanel` で、
ナビゲーションと真っ向から矛盾していた。ナビゲーション中だけモーダル性を解除する。
この根本原因はコパイロット帯の設計で回避しており、ソースでは未解決のまま）

### 7.2 有効な製品境界の決定（前身 §8 から。エンジン非依存）

- **マネージャー LLM の常駐はしない**: 往復増・軽快さ原則違反。
- **常時画面監視（先回り）はしない**: ホットキー／ユーザーのクリック起点を堅持。
- **ブラウザ拡張（DOM直読み）は標準経路にしない**: ゼロインテグレーションが差別化の核。
  ただし却下ではなく個社対応パッケージ（アップセル）の選択肢として保持（2026-07-06決定）。
- **ローカル VLM は当面やらない**。
- **再決定（2026-07-15）**: 前身では「構造化出力への全面切替は却下（ストリーミングを失う）」
  だったが、第3次は構造化単一応答を採用する（§5）。案内文のストリーミング表示を
  どう保つか（structured streaming / message 先行出力等）は挑戦3の実装で検証する。
  初トークン体感の要件自体は生きている。

### 7.3 実装上の教訓（前身から）

- **「モデルが何を・コードがどこを」の契約は、コード側の解決が決定論的に正しくて初めて
  成立する**（ラベル解決の段階マッチ「完全一致 > 含む > 部分一致」でも同名重複は救えない
  — だから candidate ID）。
- 履歴に注入した指示はステートレスAPIでは**全ターンに再生**される。初手専用指示の
  履歴混入がマーカー全滅を起こした（第1次）・進捗ターンの1行化を起こした（第2次）。
- クリップボード・パネルフォーカスなど**アプリの外側の状態**が体験を壊すことがある。
  エンジンの精度と切り分けて調査する。
