## 1. 確定した戦略スタンス（オーナー決定）

1. **時間軸＝エアポケット論**: 3〜5年後にOS/モデルレイヤーがすべてを巻き取るとしても、それまでの期間は逆に空白地帯。バリューポイントは時間で動き続けるのが当然であり、**アプリケーションレイヤーの最高のチューニングとユースケースの発見で事業のスタートを切れれば短期的には成功**。その後の戦い方はその後の話。
2. **福祉機器ビジョンは北極星、ただし先頭に立てない**: 「心につける福祉機器」を打ち出しすぎると大多数に "Not for me" になる。ボトルネックは常に人間側にあり、**人間のI/Oを100%AIに任せることはない**（自分の言葉で伝えたいとき、自分の目で見たいときは必ず残る）。だから**人間に最も近いレイヤー（あるいは今より一つでも近いレイヤー）を押さえる**ことが本筋。

## 2. 新アイデア: ツール個別ナビゲーション・ハーネス

### 内容

受信（Output）側の Vision を、**「実在の著名ツールの操作を業務解像度ほぼ100%でナビゲーションできる」**ところまで個別特化する。

- 対象例: Salesforce、Google Analytics、HubSpot、freee、マネーフォワード、SmartHR、e-tax、自治体・行政手続き
- これらのUIと操作は**有限**であり、全理解させることが可能
- 体験: ヘルプやマニュアルは「LLMに聞けばわかる」が、**聞くこと自体が面倒**。ホットキー1発で「この画面のこれをこうしたい」がナビゲーションされる（カーナビ）
- **ゼロ・インテグレーションが核心**: 入力（スクリーン）と出力（ナビ/注入）だけで完結し、System of Record にも System of Action にも触らない。API連携不要、ユーザーの行動変容も学習も不要。「freeeの使い方が全部わかります」と言えた瞬間、企業導入の温度感が変わる

### 評価（Claude）: 筋がいい。理由は3つ

1. **"Not for me" 問題を解く**。「コミュニケーション安全レイヤー」は抽象的だが「freeeがわかる」「GA4がわかる」は具体的な購買対象（SKU）になる。普遍ビジョンを個別の値札に変換する装置。
2. **ゼロ・インテグレーションは本物のGTM資産**。エンタープライズ導入の二大障壁（システム連携・行動変容）が両方ない。エージェント型ブラウザより導入が軽い、の主張は成立する。
3. **予算カテゴリが既に存在する**: Digital Adoption Platform（WalkMe / Pendo / Whatfix）。WalkMe は SAP に約15億ドルで買収された（2024年）＝この予算線は実在する。既存DAPは「管理者がツアーを作り込む・JS注入する」モデルであり、**「オーサリング不要・注入不要・デスクトップ含む全アプリ対応のVLMネイティブDAP」**は明確な世代差別化になる。投資家への説明も「WalkMeのゼロセットアップ版」で一発で通じる。

さらに、これはピボットではない。マスタープランの Vision 完成形（役所の申請・病院のWeb問診・会計ソフト）と fill_form／タスクセッションの階段そのものであり、**新しいのは「名指しのツール」を先に選んで商品化する順序**だけ。

### 直すべき点（2つ）

1. **メカニズムは fine-tuning ではなくハーネス（知識パック）方式にする**。マスタープラン §3.1 の原則（fine-tuning しない。構造化カード＋検索で実現しモデル世代交代に追従）はここでも正しい。SaaS の UI は頻繁に変わるため、焼き込んだ重みは腐る。ハーネス＝「公式ドキュメントのRAG＋UIマップ＋タスクレシピ（この目的ならこの手順）」の更新可能なパッケージとして作る。マスタープランの「私設ベンチ（ゴールデンセット）＝波検知器」は、そのまま**ハーネスの品質保証資産＝製品資産**に昇格する。
2. **勝負のメトリクスは誤ナビ率と速度**。「聞くのが面倒」を解決するには、ホットキー→答えが **ChatGPTに聞くより速く・正確** でなければならない（目安: 5秒以内に第一歩が出る）。「次にここを押す」が一度でも間違うと信頼が死ぬのは誤介入率の議論と同型。機能数ではなくこの2つで管理する。

### 競合の正直な地図

- **汎用の脅威**: Gemini in Chrome / Copilot Vision が「画面を見て助ける」の汎用版を最速で出す。ブラウザSaaS（GA、Salesforce）はまさにその着弾点。→ 防御は①ツール個別の深度（タスクレシピ・ゴールデンセット）②ブラウザ外含むデスクトップ全域③ゼロ設定④入力側（トゲ取り・注入・コンテクスト）との統合。
- **ベンダー内蔵AI**（freee のAI機能、Salesforce Agentforce 等）: 自アプリの中しか見えない。実際の業務は「freeeとExcelとメールと銀行サイト」を横断する。**横断こそレイヤーの席**。またベンダーのヘルプは自社に不利な導線（他ツールへのエクスポート等）を案内できない。
- **エアポケットの深さで言えば行政系が最深**: 役所・e-tax は誰も良いヘルプを作りに来ない領域であり、ミッション（認知の義肢）と完全に一致する。

### 楔ツールの選定基準と候補

基準: (a) 非専門家が強制的に使い、困っている (b) 買い手に予算がある (c) UI変化に耐えるハーネス更新が回る (d) 自分一人で検証できる。

| 候補 | 強み | 留意 |
|---|---|---|
| **freee / マネーフォワード** | SMBの経理は「わからないのに強制」の典型。B2B温度感の検証に最適 | ベンダー自身のAI強化と競合/提携の両面 |
| **GA4** | 「わからない」の代名詞。マーケター横断・グローバル | ブラウザ内のためGemini着弾が最速 |
| **e-tax / 確定申告** | 最深のエアポケット。個人・SMB・季節性スパイク。ミッション直結 | 買い手は個人＝単価低い。C向け話題化の武器 |
| Salesforce | エンタープライズ予算が大きい | Agentforce と正面衝突 |

推奨: **B2B温度感の確認は freee か GA4 で1本、ミッション・話題性は e-tax** の2枚看板から1つ選んで始める。

## 3. 開発への含意（次セッションの入口）

現状の受信側 Vision はモックアップレベル（1ショットの状況解釈）。ナビゲーションとして成立させるための不足は:

1. **エンドツーエンドで1ツール成立させる**: ホットキー → キャプチャ → 「この画面でこれをしたい」（音声/テキスト）→ ステップナビ（「次にここを押す」）→ 再キャプチャで進捗検証 → 次ステップ。マスタープランのタスクセッション（複数画面の手続き進行）の最小実装。
2. **画面オーバーレイ表示**: 「ここ」を指すための透明オーバーレイウィンドウ（対象要素のハイライト/バウンディングボックス）。mac アプリの新規ケーパビリティ。軽快さ最優先の原則に従い、常駐監視はせずホットキー起点を維持する。
3. **ハーネスの器**: ツール別知識パック（ドキュメントRAG＋UIマップ＋タスクレシピ）を Gateway 側（`prompt_profiles` 系の既存スキーマ）に載せる設計。クライアントは今まで通りセンサー＆アクチュエータに徹する。
4. **ゴールデンセット**: 選定ツールの実画面×代表タスク×期待ナビのベンチを最初に作る（私設ベンチの製品資産化）。誤ナビ率・初手までの秒数を毎ビルドで計測。
5. **セキュリティ前提**: 業務画面のスクショにはPIIが写る。エッジでのマスキング/最小化の方針を設計に含める（プライバシー原則 §3.4 と同じ約束を守る）。

## 4. 一貫性の確認（ビジョン ↔ この楔）
