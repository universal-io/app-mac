# POC: 画面ナビゲーター（汎用 + GA4ハーネス）— 実装計画 v2

作成: 2026-07-05 ／ 改訂: 2026-07-05（オーナーフィードバック反映）
背景: `docs/pitch/vision-and-dev-direction.md`（ツール個別ナビゲーション・ハーネス構想）の最初の実装。題材は Google Analytics 4、代表シナリオは「あるページの直帰率を見たい」。

## 0. 目的（v2 で明確化）

**プレゼンテーションで驚かせる最高の速度と最高の精度**。そのためなら土台からの再設計も許容する。

体験: ホットキー1発 =「この画面を解釈してほしい」という意図。どんな画面でも案内され、しかも爆速。

成否は機能数ではなく数字で管理する:

| メトリクス | 目標 |
|---|---|
| 初手表示までの秒数（初トークン） | ≦1.5秒（体感: 押した瞬間に反応） |
| 誤ナビ率（間違った場所を指した率） | ゴールデンセットで計測・毎ビルド追跡 |
| ハーネス有無の回答率差分（汎用 vs 汎用+GA4パック） | 差分そのものがピッチの証拠になる |

## 1. 設計原則（オーナー決定 2026-07-05）

### 1-a. 汎用ファースト。ハーネスは非可視のサーバー側アドオン

- UI は本来誰が見ても分かるようにできており、認知負荷が高いだけ。**素の VLM で解釈できる範囲が基本**であり、ユーザーに「GA4モード」等を選ばせることは絶対にしない（面倒でできない＝ゼロ・インテグレーション思想に反する）。
- ハーネスは**業務利用で誤入力回避レベルの精度が要るときの追加レイヤー**。クライアントはヒント（アプリ名・ウィンドウタイトル・AXから取れるURL）を送るだけで、Gateway が該当パックを自動選択して注入する。該当なしなら汎用プロンプトで動く——つまり初日から「どんな画面でも動く」。
- 対象ツール（Salesforce / freee / HubSpot / GA4 / Slack / e-tax…）は多いが**有限**なので作り切れる。さらに同じ器で**自社基幹システム・オンプレ・無名ツール**にもパックを足せる——それがハーネスというレイヤーが存在する意義。
- クライアントは今後もセンサー&アクチュエータに徹する（ハーネス追加＝サーバー側の変更のみ）。

### 1-b. 初手（キャプチャ直後の自動解釈）は適応型

キャプチャした瞬間、ユーザーが何をしたいかはまだ分からない（過去コンテクストのトラッキングはしていない）。だから:

- **ツール画面**: 最小限の現状認識1行のみ（「GA4 の探索レポート画面のようです」）→ すぐ意図を聞く（入力欄フォーカス）。先回りの詳細ナビはしない。**シンプルなナビが価値なのに初手から情報量が多いと理解できない**。
- **コミュニケーション画面**（Gmail / Slack 等で相手のメッセージへの返信が明らかな場面）: ユーザーのアクションは自明なので**先回りして提案**する（現行 Vision の挙動＝状況→求められていること→文案）。
- 判定はモデル自身が1コール内で行う（プロンプトで分岐: 明白な pending アクションがあれば先回り、なければ1行のみで停止）。
- **初手コール自体の要否は未確定**（「意図を聞くだけ」の方が良い可能性も残る）→ 自動初手は**トグル可能**に実装し、計測して決める。無駄コスト懸念は「軽量モデル＋低トークン＋縮小画像」でほぼゼロ化でき、初手のシーン認識は第2ターンのコンテクストシードとしても機能する。

## 2. 速度の背骨（この POC の本体）

「ChatGPT に聞くより速い」はここで決まる。実装順に:

1. **画像縮小**: ナビ用途は長辺 ~1600px・JPEG 0.7（150〜400KB）。現行 `GatewayVisionClient` の「3MB 超過時のみ再圧縮」はナビには過大。アップロードと推論の両方が速くなり、コストも下がる。
2. **ローカルOCR併用**: Apple Vision framework（`VNRecognizeTextRequest`、~300ms・端末内完結）で画面テキストを抽出し画像と併送。→ 画像をさらに小さくでき、文字読み取り精度はむしろ上がる。AXテキスト（`SituationalContextService`）も併送。端末内で処理を済ませ小さく送る方向はプライバシー原則とも同じ向き。
3. **SSEストリーミング**: review 側（`web/lib/server/review-engine.ts` / `GatewayReviewClient.swift`）のパターンを vision/navigate へ移植。初トークンが出た瞬間から表示。
4. **段階モデル**: 初手の一言＝Groq の vision 対応モデル（llama-4-scout 系、初トークンがサブ秒級）、質問ターン＝`gpt-5.4-mini`（vision-engine 既定）。review 側で実証済みの「速い Groq／賢い OpenAI」の役割分担を vision にも適用。精度はゴールデンセットで検証してから確定。
5. **接続の事前ウォーム**: オーバーレイが開いた瞬間に Gateway へ TLS 接続を張っておく（キャプチャ確定時のハンドシェイク往復を消す）。

## 3. 既存資産と不足（調査結果: 2026-07-05 時点のコード）

### 既にある（流用する）
- ジェスチャ: `BombSquad/Services/ShiftGestureMonitor.swift`（右Shift 1回/2回/長押し、window 0.35s）
- キャプチャ: `BombSquad/Services/ScreenshotCaptureService.swift`（ScreenCaptureKit、全画面/領域、>4096pxで1/2縮小）
- Vision API: `BombSquad/Services/GatewayVisionClient.swift` → `POST /api/ai/vision` → `web/lib/server/vision-engine.ts`（OpenAI Responses API、既定 `gpt-5.4-mini`、単発JSON・非ストリーミング）
- 2ペインUI: `VisionPanelView`（`BombSquad/Views/ReviewPanelView.swift`）— 左にスクショ表示済み
- SSE参照実装: review側（`web/lib/server/review-engine.ts` / `GatewayReviewClient.swift`）
- 透過オーバーレイ窓の雛形: `ScreenshotCaptureCueView`（borderless・`.screenSaver`・`ignoresMouseEvents`・全Space）と座標変換ロジック（`captureRegion` の scale/反転）
- AX走査: `SituationalContextService.swift`（要素ツリーDFS。現状テキストのみ、**位置未取得**）
- 入力欄部品: `SendableTextEditor`（Enter送信/Esc閉じる）
- 音声入力: 右Shift長押し ASR（質問を喋って聞ける）

### 無い（作る）
1. ナビ用チャットUI（`visionInstruction` は宣言のみで未配線。入力欄なし）
2. マルチターン会話状態（VM・APIとも単発のみ）
3. SSEストリーミング（vision系）
4. ローカルOCR
5. ハーネスの器（Gateway側のパック自動選択。現状プロンプトは `web/lib/server/prompts.ts` 等にハードコード）
6. 任意座標のハイライトオーバーレイ＋AX位置取得（後段）

## 4. 実装ステップ

### Step 0: 速度の背骨（目安1〜2日）— 既存 Vision の体感を別物にする
- クライアント: 画像縮小（長辺~1600px JPEG）、ローカルOCR（`VNRecognizeTextRequest`）、接続ウォーム
- Gateway: 新ルート `web/app/api/ai/navigate/route.ts`（**SSE**。review-engine のパターン移植。auth / recordUsage 流用）
- 自動初手（適応型・トグル可能）: キャプチャ確定と同時に発火。ツール画面なら1行、コミュニケーション画面なら先回り提案
- 完了条件: キャプチャ確定→初トークン ≦1.5秒（実測ログ付き）

### Step 1: チャットターン + ハーネスの器 + GA4パックv0（目安2〜3日）— ここで価値実証
- リクエスト: `messages[]`（role/text、画像はターンに添付）＋ `hints`（app_name / window_title / url）。**クライアントはハーネスを指定しない**
- Gateway がヒントからハーネスを自動選択（`window_title` に "Google Analytics" 等 → GA4パック注入。該当なし → 汎用プロンプト）
- ハーネスv0 = GA4 の UIマップ（レポート階層の有限構造）＋タスクレシピのプロンプトパック直書き（`prompts.ts` 方式。後に RAG/レシピ化）。※直帰率は GA4 の既定レポートに無く「レポートのカスタマイズで指標追加」or「エンゲージメント率の逆数」が正解──ハーネスの価値を示す絶好のデモ
- クライアント: `VisionPanelView` 右ペインを「初手（1行 or 先回り提案）→会話トランスクリプト→入力欄（`SendableTextEditor` 流用）」に。会話配列を VM に追加
- 履歴で送る画像は「最初の1枚＋最新の1枚」に制限。「撮り直す」は会話ターンとして追加（セッション継続）
- 完了条件: 直帰率シナリオが音声/テキスト質問→言語的ナビ（「左メニューの『レポート』→…」）で通る

### Step 2: パネル内ハイライト（目安2〜3日）
- モデルに正規化座標（0–1000）で `target_box` を出させる（構造化出力に `locator: {verbal, box?, confidence}` を追加）
- **契約: verbal（「右ペインの上から3番目」）は必須、box は任意**。座標が低確信なら言語だけ返す——精度不足が UX を壊さない設計
- 左ペインの `Image` に矩形を重ね描画

### Step 3: 実画面ライブハイライト（目安3〜5日）
- `HighlightOverlayWindow` を新設（`ScreenshotCaptureCueView` の雛形を流用、数秒で自動消滅）
- 座標変換: キャプチャ矩形→スクリーンポイント（`captureRegion` の逆変換）。マルチディスプレイ・Retina対応
- 精度向上オプション（AXハイブリッド）: `SituationalContextService` に `kAXPositionAttribute`/`kAXSizeAttribute` 取得を追加し、**VLMが対象の文字列を言い、AXがその文字列の要素矩形を引く**（VLM=何を、AX=どこ）。マスタープランの Vision×AX fill_form の前哨戦
- ブラウザのAXは要素露出が不完全な場合あり（Chromeは支援技術接続時のみ完全ツリー）。ダメならVLM座標にフォールバック

### Step 4（並行・継続）: ゴールデンセットと計測
- GA4 実画面 × 代表質問 × 期待ナビ（正解パス・正解位置）を20〜30件
- `web/` にエンジン直叩きの評価スクリプトを置き、**誤ナビ率・初手秒数・ハーネス有無の回答率差分**を毎ビルド計測（私設ベンチの製品資産化、マスタープラン「波検知器」と同一物）
- 自動初手の要否（1行認識 vs 意図を聞くだけ）もここで判定

### ジェスチャについて
現行の右Shift 2回（空の原文欄 → Vision）に**そのまま相乗り**する。専用ジェスチャ（4回タップ等）は体験が固まってから検討（現行は2回で `advance()` が発火するため4回は「2回×2」と衝突する。導入するなら `ShiftGestureMonitor` をタップ数カウント方式に拡張）。

## 5. モデル選定と座標精度

- Step 0/1（言語ナビ）: 初手=Groq vision 系（速度）、質問ターン=`gpt-5.4-mini`（既定）で開始。ゴールデンセットで入れ替え判断
- Step 2/3（座標）: 座標グラウンディングは computer-use 学習済みモデルが強い。Gateway の vision は現在 OpenAI 直（Anthropic は未配線）。**ゴールデンセットで現行モデルの座標精度を測ってから**、不足なら `vision-engine.ts` に Anthropic を配線する（クライアント変更不要）
- コスト: 1ターン数円以内。速度優先の縮小画像がコストも下げる

## 6. 検討して却下した代替案

- **ブラウザ拡張（DOM直読み）**: 汎用経路としては採用しない（「デスクトップ全域・ゼロインテグレーション」が差別化の核であり、標準体験を拡張に依存させない）。ただし**却下ではない**（オーナー訂正 2026-07-06）: 拡張や DOM 連携は**個社対応パッケージ（アップセル）の選択肢として保持**する。各社ごとの個社対応は DX 予算が付く有効なアップセル手段で、売上トップラインを押し上げる戦略ポイント。個社対応部隊 / FDE 的体制が整った段階、あるいは初期に大手一社へ深く張り付いてプロダクトを伸ばす戦術でも成立する。競合（Gemini in Chrome）がこの経路で来ることは引き続き前提として織り込む
- **AXテキストのみ（画像なし）**: 最速だが、Chrome の AX ツリーは不完全な場合がありレイアウト情報も失う。ハイブリッド（縮小画像＋OCR/AXテキスト）が最良
- **ローカルVLM**: 軽快さ・堅牢さ最優先の原則に反するため当面やらない
- **常時画面理解（ホットキー不要で先回り）**: 同上。ホットキー起点を堅持

## 7. リスクと逃げ道

| リスク | 逃げ道 |
|---|---|
| VLM座標がずれる | verbal locator 必須の契約（「上から3番目」）＋低確信時は座標を出さない |
| GA4のUI変更 | ハーネスはプロンプト（後にRAG/レシピ）なので即日更新可。fine-tuningしない方針の勝ち筋 |
| 業務画面のPII | ナビ用途でも画像はGateway経由・保存しない現行方針を維持。縮小・OCR併用は送信データ最小化の方向。エッジマスキングは将来課題として明記 |
| 初手の自動コールが体験的に無駄 | トグル可能に実装し、Step 4 の計測で「1行認識 vs 意図を聞くだけ」を判定 |
| パネルの実装が重くなる | 軽快さ最優先。常駐監視・自動キャプチャはしない。ホットキー起点を堅持 |
