## 正のユーザー体験: ナビゲーションモード（2026-07-07 オーナー仕様）

実装・レビューはこの体験に照らして判断する。

> **「開始」を押したら、あとは画面の光る場所を順番に押していくだけで、目的の答えにたどり着く。**

1. 質問すると、回答と一緒に「ナビゲーション開始（Nステップ）」ボタンが提案される（プランナー）。
2. 開始を押すと、パネルは**画面右下の小さな帯**に変形する。帯には「ステップ x/y・目的・現在の指示・
   終了ボタン」だけがある。中央の大パネルは邪魔なので出さない。
3. 現在のステップの対象が**実画面上で赤くハイライトされ、消えない**（次のステップに進むまで出続ける）。
4. ユーザーがハイライトされた場所を**自分でクリック**する。ナビゲーションモード中は
   「◯◯を押す」承認ボタンは**出さない**（2系統の操作が並ぶと誰も理解できない）。
5. **パネルの外をクリックしてもナビゲーションは終わらない**。むしろ外をクリックすることが
   ナビゲーションの本体。クリックを検知したら自動で画面を撮り直して進捗を確認し、
   - 進んでいれば次のステップをハイライト（ステップ表示が x/y → x+1/y に進む）
   - ミスクリックなら「まだです」と同じ場所を再ハイライト
   （「撮り直す」を手で押す必要はない。帯に手動の「撮り直す」も残す＝自動検知の保険）
6. 最後のステップでは案内ではなく**目的の答えを読み上げて**完了（「mobile は◯◯件、△△%です」）。
   完了したら通常パネルに戻って結果を見せる。
7. 帯の「終了」またはショートカット（右Shift2回）でいつでも離脱できる。

背景（2026-07-07 の実機フィードバック）: 従来パネルは「外に触れたら閉じるモーダル」
（`handleResignActive` → `closePanel`）で、これは送信レビューには正しいがナビゲーションとは
真っ向から矛盾していた（外を押した瞬間にセッションごと破棄・ハイライトも数秒で消滅・
承認ボタンと自分で押すの2系統が並存）。ナビゲーションモード中だけこのモーダル性を解除する。

## 0. 背景と診断

### 症状
ナビゲート（マーカー→ハイライト）が出たり出なかったりする。開発が進むにつれ「不親切」になった。
GA4 実セッションで、画面内に見えている「ライブラリ」を言葉では案内しながらマーカーを付けない事例を確認。

### 直接原因（コミット 821f6cb で混入）
1. `FIRST_TURN_INSTRUCTION` に追加した「初手ではマーカーを一切付けない」が、API のステートレス性により
   **フォローアップの全リクエストでも履歴の1通目として再注入**され、会話全体のマーカー抑制として効いていた。
2. マーカー付与ルールの逃げ道（「確信が低い場合は付けなくてよい」）が広く、座標に保守的なモデルが
   [[loc]] とセットの前提で**マーカー丸ごと省略**に倒れていた。
3. マーカー無しの自分の過去回答を模倣するドリフトが 1・2 を増幅。

### 構造原因（本計画の主題）
毎ターン1回の LLM コールに「今どのモードか・目的は何か・手順のどこにいるか・次の一歩は何か・
画面のどこか」の5判断を全部同時に任せている。プロンプトは5判断すべてに同時に効かせる必要があり、
どれか1つがブレると体験全体がブレる。**モデルを賢くしても構造的には解決しない。**

## 1. 設計原則: モードと計画はデータ、LLM は目と口

LLM でなければできないのは「画面理解」と「文章生成」だけ。残りは状態とコードで決定論的に持つ。

| 判断 | 担い手 | 実現方法 |
|---|---|---|
| どのツールの画面か | ルール | hints のマッチ（`selectHarness`。実装済み） |
| 今どのモードか | 状態機械 | セッション状態＋UI 操作で遷移（Phase 2） |
| 目的（ゴール）は何か | データ | 意図表明時に1回だけ生成する Task オブジェクト（Phase 2） |
| 手順のどこにいるか | データ | Task.currentStep（Phase 2） |
| 次の一歩は何か | LLM（狭いタスク） | 「この step は今の画面のどこ？完了した？」のみ |
| 画面のどこか（位置） | コード | model=「何」、OCR/AX=「どこ」の精度ラダー（Phase 1） |
| 文章（説明・文案） | LLM | 従来どおり |
| マーカーの付与 | コード | サーバー側検証＋補追コール（Phase 1） |

マネージャー LLM の常駐は往復増で軽快さ原則に反するため入れない。まずはルールベースの検証＋
補追で縛り、ルールで書けない判断が実データで問題になってから昇格を検討する。

## 2. Phase 1: 位置契約の反転＋サーバー側強制（現症状の直接治療）

変更は Gateway（[navigate-engine.ts](../web/lib/server/navigate-engine.ts)）のみ。クライアントは
target のみ（座標なし）のマーカーを既に解決できる（`NavigatorLocator` は box/target/fill を独立に
解釈、`resolveHighlightRect` の精度ラダー = OCR 実測 → VLM 座標、承認実行は `AXActionService` が
ラベルから要素を引く）。

### 2-a. 初手指示の履歴差し替え
フォローアップのリクエストでは、履歴1通目（自動初手）に付ける指示文を
「（ホットキー直後の自動初手。画面認識の1文だけを求めた）」という中立な注釈に差し替え、
マーカー禁止文を会話から消す。禁止は初手を生成するリクエスト（messages.length == 1）だけに効かせる。

### 2-b. マーカー契約の反転（プロンプト改訂）
- **主契約は [[target:表示文字列]]**。位置解決は端末側が OCR/AX で行うため、座標に自信が無くても
  target は必ず出せる——「確信が低いから丸ごと省略」の逃げ道を塞ぐ。
- [[loc:…]] は座標にも自信がある場合の追加情報に格下げ。ラベルの無いアイコンのみ loc 単独可。
- マーカー無しが許されるのは「対象が画面内に見えていない」場合だけ。
- 積極性の原則を明文化: 当てずっぽうの断定は禁止。ただし画面上の場所で答えられる質問には
  必ず場所を示して答える。

### 2-c. ロケーター補追コール（ルールベースの強制）
本文ストリーム完了後、フォローアップターンなのにマーカーが無い場合のみ、同モデルに小さな
非ストリーミングコールを1回だけ投げる:「直前の回答が画面上の要素を指しているなら
[[target:…]] を1つだけ出力。指していないなら NONE」。有効なマーカーが返れば delta として
本文末尾に補追する。クライアントはストリーミング表示からマーカーを逐次除去している
（`ReviewPanelView` → `NavigatorLocator.strippingMarkers`）ため、**補追はユーザーに見えず、
最終パースでハイライトとして拾われる**。補追コールの失敗は無視（best-effort）。

### 2-d. 計測の種
usage metadata に `has_locator`（最終テキストにマーカー有無）と `locator_supplemented`
（補追が発動したか）を記録。マーカー付与率と「素のモデルの契約遵守率」を admin/SQL で追える。

### 完了条件
GA4 実画面での質問ターンにおいて、画面内に対象が見えている質問でハイライトが出ること。
補追発動率が計測できること。

### 2-e. 実機検証で見つかった修正（2026-07-06）
1. **ハーネス不一致**: クライアントは URL ヒントを送っておらず、Chrome のウィンドウタイトルは
   「アナリティクス」のみ → GA4 ハーネスが一度もマッチしていなかった（ヘッダーの「· ga4」
   サフィックス欠落で発見）。タイトル単体の「アナリティクス」もマッチ対象に追加。
   恒久対応はクライアントからの URL ヒント送信（AX でブラウザの URL を取得。残タスク）。
2. **ラベル解決の段階マッチ化**: [[loc]] 任意化により、OCR/AX の解決で複数ヒット時の
   曖昧さが表面化（target「ユーザーの環境の詳細」に対し部分一致の「ユーザー」を選び、
   誤ハイライト＋誤クリックで展開メニューを閉じた）。OCR（`resolveHighlightRect`）と
   AX（`AXActionService`）の両方を「完全一致 > 候補がラベルを含む > 部分一致」の
   段階式に統一。教訓: **「モデルが何を・コードがどこを」の契約は、コード側の解決が
   決定論的に正しくて初めて成立する**。

## 3. Phase 2: Task オブジェクト＋レシピ化（構造の本丸）

### 3-a. Task オブジェクト
ユーザーの意図表明を検知したら（当面はハーネス該当ツール＋質問文があるターン）、**1回だけ**
プランナーコールを実行し、構造化 Task を生成する:

```jsonc
{
  "tool": "ga4",
  "goal": "コンタクトフォームの月次セッション数を知る",
  "steps": [
    { "verbal": "左メニューの「エンゲージメント」を開く", "target": "エンゲージメント" },
    { "verbal": "「ページとスクリーン」を開く", "target": "ページとスクリーン" },
    { "verbal": "表の検索欄にページパスを入力", "target": "検索", "fill": "/contact" },
    { "verbal": "期間を先月に変更", "target": "過去28日間" },
    { "verbal": "「セッション」列の数値を読む", "target": null }
  ],
  "currentStep": 0
}
```

- v3の現行置き場: Gatewayはステートレスで、クライアント（VM）が保持して`input.task`で送る。
  **v4移行先**: Gatewayがrunの唯一のwriterとなり、Supabaseの最小run rowと署名付きTask snapshotを
  revision付きで管理する。クライアントは表示cacheと輸送を担うが、単独でstepを進めない。
  詳細はaccuracy plan §0.6「Runの所有権」を正とする。
- 以降の各ターンの LLM の仕事は「この step は今の画面のどこか／完了したか」に縮小する。
  最終 step は案内ではなく**読み上げ**（「先月の /contact のセッションは 154 です」）——
  ここで初めてユーザーの目的が達成される。

### 3-b. ハーネスのレシピデータ化
[harness.ts](../web/lib/server/harness.ts) のプロース（タスクレシピ）を Task.steps の候補データに
進化させる。プランナーはレシピに該当があればそれを採用（決定論）、無ければ自由生成（LLM）。
レシピはそのままゴールデンセットの正解データを兼ねる。ツールを増やす単位も「レシピ追加」で明確化
（GA4 → Slack → Notion…ユーザー数の多い順）。

### 3-c. モード状態機械
```
待機 → シーン認識（自動初手） → 意図確定（Task 生成）
     → 「ナビゲーションを開始しますか？」（UI ボタン＝決定論的遷移）
     → ガイド実行（コパイロット） → 完了 / 離脱
```
モードは VM のセッション状態。モデルに毎ターン再判断させない。

## 4. Phase 3: コパイロット UX

- ガイド実行に入ったら、中央の大パネルから**画面右下にドッキングした小さな帯**に変形。
  「ここです（ライブハイライト）→ ユーザーが操作 or 承認 → 自動再キャプチャ → 次の step」のループ。
- 再キャプチャはユーザー操作後の短い監視窓だけ行い、常時録画しない。v3の画像pollingをfallbackに、
  v4ではSCStream dirty rect/idle frameとAXObserver通知を変化開始signalとして評価する。
- 凍結中の「合成クリック後のパネル復帰」問題（旧 v2 の残タスク。真因は後日判明=resignActive）は、パネルが最初から
  非アクティベートの端の帯であれば「復帰」という概念自体が消える可能性が高い——コパイロット UX が
  バグの迂回路を兼ねる。着手時に [Action] ログで closePanel 呼び出し元の特定から。

## 5. Phase 4（並行・継続): 計測

- Phase 1d の `has_locator` / `locator_supplemented` でマーカー付与率を毎日追う。
- レシピ（3-b）＝ゴールデンセット。誤ナビ率・初手秒数・ハーネス有無差分は v2 の計画を継続。
- プロンプト・モデルを変えるたびに退行を数値で検出する。モデル変更（Gemini 座標系・並列第2コール）は
  計測ができてから判断する。

## 6. 実装順

1. **Phase 1**: 2-a〜2-d。Gateway のみ。**実装済み（2026-07-06、コミット 0858685。実機確認済み）**
2. **Phase 2**: Task オブジェクト＋レシピ化＋状態機械。API 契約に `input.task` 追加。
   **実装済み（2026-07-06）**: プランナーは本文ストリームと並行実行、レシピ3件（GA4）、
   モード遷移は「ナビゲーション開始」ボタン、進行は [[step:done]] マーカーでクライアントが
   currentStep を前進。制約: 承認実行（AXクリック）は従来どおり1セッション1アクションのまま
   （パネル復帰問題。Phase 3 で解消見込み）。コパイロット中はユーザーが自分でクリック →
   「撮り直す」で step 検証・前進するのが基本ループ。
3. **Phase 3**: コパイロット UX（右下ドック帯・ステップ実行ループ）。
   **実装済み（2026-07-07）**: 正の UX 仕様は本書冒頭「正のユーザー体験」。
   ナビ開始でパネルが右下の帯（`CopilotStripView`）に変形し、外クリックで閉じない
   （`handleResignActive` を copilot 中だけ解除）。ハイライトはステップ前進まで永続。
   グローバルクリック監視 → 1.2秒デバウンス → 無音の全画面キャプチャ → 検証ターン →
   [[step:done]] で自動前進。承認ボタンはコパイロット中は出さない（操作は
   「光る場所を自分でクリック」の1系統のみ）。完了時は通常パネルに戻して答えを表示。
   ※これにより凍結中だった「合成クリック後のパネル復帰」は迂回された（合成クリック
   自体を使わないため）。承認駆動の合成クリック実行ループは将来の任意課題に格下げ。
4. Phase 4 は 1 の直後から常時。

## 7. チューニング課題（2026-07-07 実機評価。機能は動くが精度は未実用）

実機テストで「機能自体は成立、案内の中身がデタラメになるケースあり」を確認。実例:
質問「国や地域などの閲覧元を確認する」に対し、プランがテクノロジー→概要へ誘導
（国・地域はユーザー属性の領域。トピック不一致）。さらに左メニューに「概要」が
3箇所あり、ハイライトが**別の「概要」**（ビジネス目標配下）に付いた。

### 課題リスト
1. **プランの知識精度**: レシピに無い目的でプランナーが誤った経路を作る。レシピが
   少ないうちは「レシピの例に引っ張られて似た経路を選ぶ」バイアスも疑われる。
   → レシピ拡充（本コミットで国・地域を追加）＋ UIマップに「どのセクションが何の
   トピックか」を明記。恒久対策は Phase 4 ゴールデンセットでの誤ナビ率計測。
2. **重複ラベルの特定不能**: 「概要」のような汎用ラベルは画面内に複数あり、
   target 文字列の完全一致だけでは原理的に特定できない。
   → 暫定: 重複がありうる場合は [[loc]] 併記をプロンプトで必須化（本コミット）。
   構造対策（次の設計課題）: **端末側で OCR/AX から候補一覧（ラベル＋位置＋周辺
   コンテクスト）を作ってサーバーへ送り、モデルは候補の ID を選ぶだけ**にする。
   位置の自由記述を消し、グラウンディングを選択問題に変える＝決定論化の最終形。
3. **過去文脈への引っ張られ疑い**: 検証ターンにも会話履歴全体が乗るため、前の目的
   （例: モバイル数）が現在の Task に混入しうる。
   → 検討: コパイロット中のリクエストは「Task＋最新キャプチャ＋直近1〜2ターン」に
   絞る（履歴の長さがノイズ源になっている可能性）。
4. **検証ターンの言い回し**: 「反映されています。〜を押してください」のように
   前ステップ確認と次ステップ案内が混ざり、ユーザーには冗長。ステップ検証は
   構造化出力（done: bool / 次の指示1文）に置き換える余地（§8 却下案の再評価）。

> 精度チューニングは場当たりのプロンプト修正を重ねない。**先にゴールデンセット
> （実画面×質問×正解経路20〜30件）を作って誤ナビ率を数値化**し、プロンプト・
> レシピ・モデル・候補選択方式の効果を比較して決める（Phase 4 を前倒しで最優先に）。

## 8. 検討して却下した代替案

- **構造化出力（json_schema strict）への全面切替**: マーカー必須をスキーマで強制できるが、
  トークンストリーミングを失う（初トークン≦1.5秒の背骨と衝突）。補追コール方式なら
  ストリーミングを保ったまま同等の強制ができるため、まず補追で行く。コパイロットモードの
  step 検証コール（Phase 2）は回答が短く構造的なので、そちらでは構造化出力を採用してよい。
- **マネージャー LLM の常駐**: 往復増・軽快さ原則違反。ルール検証で足りなくなってから。
- **常時画面監視（ホットキー不要で先回り）**: 軽快さ・堅牢さ最優先の原則に反する。
  ホットキー／ユーザーのクリック起点を堅持。
- **ブラウザ拡張（DOM 直読み）**: 汎用経路としては不採用（「デスクトップ全域・ゼロ
  インテグレーション」が差別化の核であり、標準体験を拡張に依存させない）。ただし**却下では
  なく個社対応パッケージ（アップセル）の選択肢として保持**（オーナー決定 2026-07-06）。
  競合（Gemini in Chrome）がこの経路で来ることは前提として織り込む。
- **AX テキストのみ（画像なし）**: 最速だが Chrome の AX ツリーは不完全な場合があり
  レイアウト情報も失う。ハイブリッド（縮小画像＋OCR/AX テキスト）が最良。
- **ローカル VLM**: 軽快さ・堅牢さ最優先の原則に反するため当面やらない。

## 9. v2 から引き継ぐ土台（旧 poc-ga-navigator.md を統合。2026-07-07）

v2 計画（2026-07-05 作成）は本書に吸収して削除した。実装の前提として生きている部分:

### 9-a. 汎用ファースト。ハーネスは非可視のサーバー側アドオン
- UI は本来誰が見ても分かるようにできており、認知負荷が高いだけ。**素の VLM で解釈できる
  範囲が基本**であり、ユーザーに「GA4 モード」等を選ばせることは絶対にしない
  （ゼロ・インテグレーション思想）。
- ハーネスは精度が要るときの追加レイヤー。クライアントはヒント（アプリ名・ウィンドウ
  タイトル・URL）を送るだけで、Gateway が該当パックを自動選択して注入。該当なしなら
  汎用プロンプトで動く＝初日からどんな画面でも動く。
- 対象ツール（Salesforce / freee / HubSpot / GA4 / Slack / e-tax…）は多いが**有限**なので
  作り切れる。同じ器で自社基幹システム・無名ツールにもパックを足せる——それがハーネスと
  いうレイヤーの存在意義。
- クライアントは今後もセンサー&アクチュエータに徹する（ハーネス追加＝サーバー側の変更のみ）。

### 9-b. 初手（キャプチャ直後の自動解釈）は適応型
- ツール画面: 現状認識1行のみ → すぐ意図を聞く（先回りの詳細ナビはしない。シンプルさが価値）。
- コミュニケーション画面（返信が自明な場面）: 先回りして状況＋返信文案を提案。
- 判定はモデル自身が1コール内で行う。自動初手はトグル可能（`AppSettings`）で、要否は計測で
  最終判断。ジェスチャは右Shift2回に相乗り（専用ジェスチャは体験が固まってから）。

### 9-c. 速度の背骨（実装済み）
「ChatGPT に聞くより速い」の根拠。目標: キャプチャ確定 → 初トークン **≦1.5秒**。
1. 画像縮小: 長辺 ~1600px・JPEG 0.7（アップロードと推論の両方が速く、コストも下がる）
2. ローカル OCR 併用: Apple Vision framework（端末内 ~300ms）。文字は OCR で正確に、画像は小さく。
   OCR 断片の実測矩形は端末に残り、[[target]] の位置解決（精度ラダー）にも使う
3. SSE ストリーミング: 初トークンから表示（出力は平文＋マーカー。JSON を挟まない）
4. 段階モデル: 初手＝Groq llama-4-scout（サブ秒級）、質問ターン＝gpt-5.4-mini
（接続の事前ウォームは未実装の改善余地）

### 9-d. モデル選定と座標精度
- 座標グラウンディングは computer-use 学習済みモデルが強い。gemini-3-flash-preview は
  座標 4/4（うち2件ピクセル級）だが初トークン4秒 → **本文は速いモデル＋座標は並列第2コール**の
  構成が候補。採否はゴールデンセット計測後（§5）。
- コスト: 1ターン数円以内。速度優先の縮小画像がコストも下げる。
